# Brick Railroad: architecture and phased roadmap

This is a browser sandbox for laying out LEGO cities from real models, with rail, roads, baseplates and MILS modules. You build with whole imported modules, connect track and roads exactly, run trains, and export a parts list you can buy.

It serves two jobs on one engine:
- **a boundless sandbox world** that you can extend in any direction, where rules are advisory;
- **a practical planner for a real layout**: draw your room and tables to scale, plan inside that footprint, and get a full parts list and a "buildable as planned" check before you buy or build anything.

Since D6 (2026-11-27) the planner leads. Brick Railroad is becoming a modern BlueBrick: the planner a LUG uses to lay out a real show, whose main surface is a fast top-down 2D plan, with 3D and Play as views of the same document (§13).

Sources: [part-data.md](research/part-data.md), [engine-stack.md](research/engine-stack.md), [connection-rules.md](research/connection-rules.md), [product-scope.md](research/product-scope.md). Facts the reports could not confirm are collected in §11 and must be checked before anyone relies on them.

## 1. One-paragraph architecture

An **offline data pipeline** (Rust plus scripts, run in CI) compiles the LDraw parts library, Rebrickable dumps, the LDraw OMR and the LDCad shadow library into a versioned, content-addressed **asset bundle** on a static CDN. That bundle holds part meshes with studs extracted, a connector database, the catalog, element-existence tables, verified set models and attribution. In the browser, a **TypeScript app** has five parts:
- a React UI shell;
- an **import worker**, the same Rust crate built for WASM, that parses `.ldr`, `.mpd` and plain-ZIP `.io` files, resolves parts and colors, computes badges, and bakes models;
- a **layout core** that holds the unbounded world of placements, exact track and road joins, plan regions with their physical footprints, and validation;
- a **sim worker** that runs trains on a derived track graph at a fixed timestep;
- a **renderer**: three.js `WebGPURenderer` with automatic WebGL2 fallback, drawing instanced and merged *models* with LODs, culled studs, SSAO and outlines. From B2 a 2D plan backend beside it draws the default top-down plan from geometry-baked glyphs (§6).

A world is a manifest plus one JSON shard of placements and laid track per super-chunk, stored in IndexedDB and exported as a file. Plan regions export separately, together with their BOMs and printable plans, and from B1 they are also saved with the world. The MVP has no backend. Accounts, cloud saves, sharing and live co-editing come in B6 (§13).

## 3. Data pipeline (offline, in CI)

### 3.1 Inputs, by part source
Every part and model comes through a **`PartSource`** plugin. Each source declares an id, provenance, a per-item license, redistribution rights and a priority used when resolving.

| Source id | Provenance | Content | License or terms | Shipped |
|---|---|---|---|---|
| `ldraw-official` | `official` | LDraw `complete.zip` | CC BY 2.0 / CC BY 4.0, with attribution | Yes |
| `ldraw-unofficial` | `unofficial` | `ldrawunf.zip`, specific parts by allowlist only | Per part | Opt-in, badged |
| `user-inline` | `custom` | Inline `0 FILE` parts or Studio CustomParts found in an import | User's own; drawn whatever licence it names, or none | No: compiled and drawn on the user's device only (§3.3) |
| `omr` | `official` model | OMR `.mpd` sets | CC BY 2.0 | Yes, after verification |
| `ldcad-shadow` | connectivity | `!LDCAD SNAP_*` metadata | CC BY-SA 4.0 | Yes, as a separate data package |
| `rebrickable` | catalog | Daily CSV dumps, plus nightly API crosswalks | Any use, attribution requested | Yes, derived tables |
| *(later)* `thirdparty-<vendor>` | `thirdParty` | Vendor track geometry and connectors | Per vendor | **No (D3)** |

### 3.2 Pipeline stages
1. **Fetch and pin.** Download the inputs, record versions and hashes, and fail if any input changes without a version bump.
2. **Attribution.** Read the `!LICENSE` header of every LDraw file and record it; no licence gates the build (owner decision, 2026-11-20). Write `attribution.json` (part to authors, license, history and a "modified" note) and a generated credits page.
3. **Catalog database.** Load the Rebrickable CSVs into SQLite at build time, then emit static, sharded, compressed outputs:
   - `colors`, `parts`, `part_relationships` and the crosswalks to LDraw and BrickLink;
   - an **element-existence table** of (part, color) pairs, as a compact sorted array or bitset that loads lazily;
   - set metadata and inventories (latest version by default; the others kept);
   - a color table merged from LDConfig (render values) and Rebrickable (canonical ids). Rebrickable color ids are the canonical key.
4. **Part compiler** (Rust crate `brick-compile`):
   1. Flatten sub-files, tracking BFC winding through the matrix determinant and `INVERTNEXT`.
   2. Keep colors 16 and 24 as placeholders.
   3. Weld vertices (ε ≈ 0.05 LDU) and smooth normals using type-2 lines as hard edges and type-5 lines as soft edges.
   4. **Extract studs** (`stud*.dat`) into stud records holding position, type and a cover-test cell.
   5. Extract the underside (tubes and anti-studs) into a submesh.
   6. Build LODs: **LOD0** from `p/48` primitives plus a small bevel on hero parts; **LOD1** from standard primitives; **LOD2** from `p/8` primitives with the underside dropped, simplified with meshoptimizer.
   7. Emit GLB palette bundles plus optional edge-line data for an instruction-style look.
   8. Never substitute logo studs.
5. **Connector build.** Merge LDCad `SNAP_*` metadata over the parts, then add connectors inferred from primitives (`stud*`, tubes, Technic `peghole`/`axlehole`/`connect*`). Convert everything to our schema (§5). Hand-curate the **city palette**: track, road plates, baseplates, train bases and bogies, Technic bricks for module joins. Run the track field-membership test (§5.3) on every track part.
6. **OMR ingest.** Parse each set, match it to its Rebrickable set by number, run model badges L1 and L2 (§7.1), and bake the model (§3.3). Sets that pass L1 and L2 exactly become "Real set" catalog entries.
7. **Publish.** Upload a content-addressed CDN bundle with a manifest (`bundleVersion`, input versions, per-source license summary).

### 3.3 Model bake
The browser import worker and the OMR ingest share the same code.
1. Unpack and parse the file. For `.io`, read `modelv2.ldr` with Studio's type-11 part lines rewritten as standard type-1 lines, which reproduces Studio's own `model.ldr` exactly, and fall back to `model.ldr`. `model2.ldr` is read only for each part's `BL_Item_No`; its embedded Studio geometry is never used. Encrypted legacy archives are rejected with a "re-save in current Studio" message.
2. Resolve each part against the pinned LDraw library: the prebuilt bundle first, then official parts compiled from the pinned mirror (unofficial parts only through the allowlist). A Studio name that isn't an LDraw part is renamed only when the BrickLink crosswalk names exactly one LDraw part that exists at the pin. Inline definitions are compared with the official part and never drawn in its place. A **custom part** (an inline part the library lacks, an inline copy that differs from its official part, or a Studio CustomParts file) is compiled from the user's own file whatever `!LICENSE` its files carry, or none, and whatever their `!LDRAW_ORG`, `Unofficial_*` included; a library file the part reaches still needs the unofficial allowlist, which governs shipped and library parts only. Its own embedded sub-files take precedence over library files of the same name, as MPD requires. It gets a content-addressed id `custom:<sha12>/<name>` over every file it reaches, a `custom` badge, connectors inferred at import (flagged unverified, never from published records), and a BOM line that is never buyable. It is drawn on the user's device only, never shipped or bundled. Parts that can't be resolved (not in the library and not a custom part, a missing subfile, an unofficial library part off the allowlist, a custom part whose files refer to each other in a loop, or an ambiguous or missing Studio part) are skipped and reported, never turned into placeholders.
3. Map colors. Instances in an unknown colour, including Studio-only codes, are skipped and reported, never snapped to a nearby colour.
4. Build the **instance list**: part id, color id and a 4×3 matrix in LDU. Keep the **submodel tree**, because bogies and vehicles need it.
5. Build the **BOM**, normalized through aliases and `part_relationships`.
6. **Remove covered studs inside the model**: a stud with an anti-stud or solid underside directly above it is dropped.
7. Derive the **base footprint**: the set of bottom-facing anti-stud cells on the lattice, plus flat-bottom regions. Layout placement uses this for support checks.
8. Compute the 2.5D occupancy (a voxel column per stud cell) and the AABB.
9. Build **merged LOD meshes** per material class: mid LOD from LOD1 parts merged; far LOD as a voxel greedy mesh at 1 stud × 1 stud × 1 plate resolution.
10. Detect vehicles by part signatures (train motors, wheels, magnetic couplers) and propose a vehicle sidecar. A vehicle is a group of touching parts that holds a wheelset. It also carries every other group that rests on it (a part whose bottom is exactly its top, overlapping it in plan) or lies wholly within its bounds, so a loose roof, sticker or seated figure rides its car. A group that more than one vehicle could carry rides the one it overlaps most in plan. A group that does neither, such as a figure standing beside the train, rides no vehicle. A train standing on the rails draws those parts on the ground the track is laid on, beside the nearest car, where they stay while Play runs.
11. Store the original file unchanged so it can be re-exported.

### 3.4 Attribution and licenses in shipped assets
- Part GLBs carry `extras.ldraw = {name, authors, license}`.
- The credits page covers LDraw, the OMR authors of each model, Rebrickable and LDCad.
- **OMR errata.** An OMR file with a provable typo is baked with a line erratum from `tools/asset-pipeline/omr-errata.json`. Each entry names the model, the file's pinned SHA-256, the line, its exact text before and after, and its evidence: the line's mirror twin or the wall course it belongs to, quoted from the same file. The pinned file stays unmodified in `.cache/omr`; only the bundle bake applies the erratum. `verify-ldraw` (which every bundle build runs first) fails when a pin, the line or an evidence line no longer reads as recorded, or when an erratum names no palette OMR model, and the bake refuses a re-pinned erratum or a line that reads otherwise. The manifest lists each model's errata, and the credits page and the credits download show them as "Modified from OMR". Errata come only from the model's own symmetry or structure; sub-LDU drift with no single intended value is left alone. Imported files are never patched: they connect as their own bricks are placed.
- The connectivity package carries its own CC BY-SA 4.0 notice and an attribution to Roland Melkert.
- The trademark disclaimer appears in the footer, the about page and every export.

### 3.5 Extension points for third-party parts (D3)
These are built now and used later:
- `PartSource` plugins with a `provenance` field. The BOM, the badges and the catalog filter all read it.
- Each `TrackProfile` declares a track system, a gauge class and an **angle step N**, where N = 16 for 22.5° steps and N = 32 for 11.25° steps (§5.3).
- A layout-level `allowThirdParty` flag that is off and hidden today. Validation refuses `thirdParty` parts unless the flag is on, and the BOM flags them.
- Catalog ids are namespaced (`ldraw:53401`, `bt:R56-curve`), so vendor packs can never collide with LDraw numbers.

Adding a vendor later means writing a source adapter, the vendor's connector data, and a profile with N = 32 if any of its pieces needs 11.25° steps. No core code changes.

**Single parts from the pinned library.** The standard bundle carries `libraryParts`, an index of every pinned part that LDraw lists in part lists (not moved, alias, `~` or baked-colour files), sits in an active LDraw category and has at least one produced colour: its title, category, keywords, Rebrickable number and produced colours (`docs/part-bundle.md`). The palette searches it only once a query has two characters, on the All tab, under its own results, and leaves out parts the palette already offers. Search ranks on that metadata alone. Picking a part in a colour writes a one-line LDraw model, `1 <colour> 0 0 0 1 0 0 0 1 0 0 0 1 <part>.dat`, and hands it to the same import as a user's file. So placing and connecting it come only from the part's own geometry, through the import and bake, exactly as the same part inside any imported file. The bytes depend only on the part and colour, so picking it again finds the stored import by its SHA-256 and adds nothing.

**Library search and filter memory.** Every library search reads one query language, BlueBrick's filter syntax, parsed once by `LibraryQuery`: words must all match, a `"quoted phrase"` matches its words in order, `-` excludes a word, phrase or number, `#` matches part and set numbers only, and a colour name narrows the colours offered. The palette's own index, the pinned library's single parts and the find palette all read it. The catalog Worker understands only plain words, so it is asked for the words a result must contain, and each of its hits is kept only when the local index admits that item under the query's exclusions, phrases and numbers. The library has two filter scopes, as BlueBrick does: one search and colour for every tab (the default), or each tab with its own search and colour. The scope, the current tab and every tab's search and colour are kept in site storage (`brr.library-filters`) and come back on the next visit. Search only chooses what the library lists; it never changes how anything places or connects.

## 5. Connector and placement schema

Positions are in **integer LDU**. x and z are the plan axes and y points up. Layout heights are counted in **plates above the top surface of the baseplate**. Floats appear only in rendering, and in imported models' internal matrices, which are never used for joins.

### 5.1 Part record (connector database)
```ts
type Provenance = "official" | "unofficial" | "custom" | "thirdParty";

interface PartRecord {
  id: string;                 // namespaced: "ldraw:53401"
  source: string;             // PartSource id
  provenance: Provenance;
  license: string;            // SPDX-like
  cityRole?: "track" | "road" | "baseplate" | "moduleJoin" | "bogie" | "motor" | "wheel";
  footprint: { poly: [number, number][]; yMin: number; yMax: number }; // LDU
  keepOut?: Volume[];         // switch levers, motors: solid for collision
  connectors: Connector[];
  trackPaths?: TrackPath[];   // sim geometry per route (switches: 2)
  roadLanes?: Lane[];         // lane centerlines, direction, turn links
  bomFlags?: ("power9V" | "powerPlastic" | "thirdParty")[];
}

type Connector =
  | { kind: "stud" | "antiStud"; pos: Vec3i; grid: 20 }
  | { kind: "trackEnd"; pose: TrackPose; system: string /* "lego-9v-plastic" */; gauge: string }
  | { kind: "roadEdge"; pos: Vec3i; heading: Rot90; lanePattern: string }
  | { kind: "moduleEdge"; profile: string; edge: "N" | "E" | "S" | "W"; slots: Vec3i[] }
  | { kind: "technicHole" | "technicPin"; pos: Vec3i; axis: Vec3i };

type TrackPath =
  | { kind: "straight"; from: number; to: number; length: Exact }         // connector indices
  | { kind: "arc"; from: number; to: number; radius: Exact; turn: number /* steps of 360/N */ };
```

### 5.2 Placement poses (layout)
```ts
type Rot90 = 0 | 1 | 2 | 3;
type LatticePose = { kind: "lattice"; x: number; z: number; yPlates: number; rot: Rot90 }; // x,z in LDU, multiples of 20 (10 where half-stud allowed)
type TrackPose  = { kind: "track"; n: 16 | 32; coeffs: bigint[] /* length n/2, studs */; heading: number /* 0..n-1 */; yPlates: number };
type Placement  = { id: string; ref: CatalogRef | ModelHash; pose: LatticePose | TrackPose; layer: Layer; locked?: boolean };
```
- **The world is unbounded.** Coordinates are signed integers in LDU. Plan coordinates need int32, which spans ±859 km, but the sandbox allows int53 (JS safe integers). Chunk key = `floor(x/640), floor(z/640)`. The renderer and validators always work relative to a chunk origin, so floats never carry large world coordinates.
- Models, baseplates and road plates always use `LatticePose`.
- **Internal mates and exposed connectors (owner decision, 2026-11-19).** When a model loads, `ModelConnectors` mates its connectors inside the model by the same rules the solver uses, and every engaging pair is an internal mate. A connector mated inside its own model never votes or joins outside it, except that it stays exposed over the free stretch that reaches an open end: a male exposes its free tip, rooted and closed at the cut, and a female exposes its free entrance stretch, closed at the cut, except over a stretch another exposed face of the same part instance, the same gender and the same axis line already covers exactly. A face covers a stretch exactly when its sections span that stretch's whole interval with compatible sections: it points the same way along the line, and at every point of the interval its section has the same kind, size and group (caps and sliding don't count). A face that covers only part of the free stretch doesn't cover it: the whole stretch stays exposed. A free tip whose cut isn't a whole sixteenth of an LDU is reported off-lattice (§5.3 / the exact-joins rule). There's no pin special case.
- *M1 S5 status:* a placement is one `World` row (`refId`, x, z, `yPlates`, `rot`); `refId` indexes the editor's catalog (the 3811 baseplate and the ten OMR sets). The model's float matrices never enter the `World`. The bake records each model's lattice phase and its AABB. Two candidates are measured. The stud phase is the majority integer x and z mod 20 of the model's lowest upright stud layer. The receptor phase is the majority whole-LDU x and z mod 20 of the receptors the model stands on: the female, downward, axis-aligned connectors of its parts' connector records, from every tier, whose height identifies (§5.3) to the model's identified underside; a tie there leaves no receptor phase. A receptor takes a stud when E6's mate rule (`SnapMating`, ported to `brick_compile::connect::Mate`) engages the measured stud with it at offset 0, the stud's root on the receptor's opening: the stud is a male round section of the stud primitives' measured radius and height, rooted on the floor, ungrouped and fixed, so a stud primitive measuring 6 by 4 LDU reads as LDCad's `stud.dat` snap (`R 6 4`, `caps=one`). Holes the stud is loose in, holders narrower than it, axle holes, blind cavities shallower than it and grouped receptors never take it: they still vote for the receptor phase, but they never vouch for their part's mesh below. A candidate seats when a stud field under the model fits it: a stud cylinder at every lattice point of that phase under the model, standing on its underside and one stud tall, meets no part's real mesh over a positive area, except that a part's own mesh is not tested at a lattice point where one of its own receptors that take a stud sits (identified sixteenths, exactly): there the connector data decides, because a clutch fit is an interference by design and many LDraw cavities are drawn inside the measured stud. Other parts' meshes are still tested there. The cylinder's radius is the stud primitives' measured inscribed radius (the distance from the stud axis to the nearest face of the outer wall, 5.885 LDU for the 16-segment standard stud, so it follows the LOD's faceting) less the 0.05 LDU weld, and its ends are shrunk by the weld too. The stud phase wins unless it doesn't seat and the receptor phase does. A tie in the stud layer gives no stud phase: the receptor phase decides if it seats, and otherwise the tie fails the bake. A model with no studs takes the receptor phase where it seats, and otherwise has no lattice. So a studless tile is phased by its anti-studs, and a jumper by the anti-studs it stands on, which leaves its centre stud half a stud off the lattice, while a 1 × 1 round plate, a turntable, a hinge plate or a custom table on round plates keeps its stud phase because its own stud field fits. The layer that sets the height is the lowest stud layer whenever the model has studs, and the underside for a model without. The pipeline reads receptors from the connector extractor and the import from the records it loads, sending each receptor's caps, slide, group and sections beside its pose (sizes as binary doubles, so they cross into WASM bit for bit); both are the same published faces, so both bake one rule. An app that sends receptor poses without their shapes bakes as if its parts had no receptors. `packages/test-fixtures/snap-mating-vectors.json` holds mating pairs, each shape as its caps (1 closes the root, 2 the far end), slide, group and sections (`[code, size, length]` in LDU), with the offset ranges, in sixteenths, over which they engage; E6's `SnapMating` (`packages/domain`) and the port (`crates/brick-compile/tests/mating.rs`) must both give every range exactly. The client shifts the model so that phase sits at 10 mod 20 like a baseplate's studs, moves the pivot to the stud corner nearest the footprint centre, and puts the AABB bottom at y = 0. Module placement poses are exact integer lattice poses: x and z at multiples of 20, whole plates, and a quarter turn about that pivot. The model's own matrices are never altered after the bake. OMR model records are baked from positions identified under §5.3's OMR rule, and any deviation that rule leaves comes from the source file and is reported. Until S6, every model sits on the baseplate top (yPlates 0). Removed slots go on a per-chunk free-list, and a `PlacementHandle` carries a generation so a stale handle is refused.
- *M1 S6 status:* the bake (§3.3 steps 6–8) also records each model's rest plane, its base footprint, and a 2.5D column per stud cell (bottom and top in whole plates above the rest plane). There is one physical table plane at y = −t, where t is the measured thickness of the 3811 body (`tablePlane` in `docs/verified-facts/geometry.json`). A placeable whose phasing layer (S5) lands on whole plates when its lowest vertex rests on the table plane, meaning that layer sits t above its underside modulo one plate, rests there, and its rest plane is the plane t above its underside. Any other placeable puts its underside on the plate lattice, so on bare ground it rests at y = 0 (its rest plane is its lowest vertex). No role, kind or thickness test is involved, so a loose 3811, the 3811 inside a MILS module or a user's model, a modular on its own baseplates and a user's model of road baseplates all end with their baseplate top at y = 0. A studs-only model on bare ground sits t above the physical table, because world poses are whole plates and resting it on the table would put its studs half a plate off the lattice. The footprint is probed at the model's lowest vertex. A column spans the lowest to the highest point of any part's real mesh (studs excluded) over the cell, read from the triangles clipped to the cell's square shrunk by the 0.05 LDU weld on each side, and counted only where the clipped area is positive. So a slope's low cells stop at its sloped face, an inverted slope's column starts at its underside, and a cell that a wedge, round corner or turned part only covers with its bounding box stays empty. The bake also records each part instance's own footing: the cells where that instance's clipped triangles reach the model's lowest band (a column bottom no higher than the lowest column bottom of the model), listed as (instance, cell) pairs by instance and then by cell. A cell two parts share is listed under each, and together the pairs are exactly the cells whose merged column reaches that band, so a plan check can leave out some of a model's parts and judge the rest by their own footing. Part AABBs only bound the cell grid. The client pivots on the footprint's bounding-box centre instead of the AABB centre (the AABB when the footprint is empty) and puts the rest plane at y = 0. The axis-aligned parts below the rest plane form the placement's slab, and two slabs never share space. `domain` keeps a per-chunk `Uint16Array` occupancy grid of column tops in plates. A placement's `yPlates` is the lowest height at which none of its columns goes below what is already in the grid: max over its occupied cells of (grid top − column bottom), and 0 on bare ground. The ghost shows one brick above that height.
- *Placement collisions:* the standard bake also records, per stud cell, one box per part that reaches into the cell: the extent of that part's mesh clipped to the cell's square (shrunk by the 0.05 LDU weld, as for the column), with each side that is the part's own face pulled in by the weld and each side the clip cut reaching the cell edge, rounded outward to sixteenths of an LDU and kept as an in-cell plan box and a height span. A part that reaches no more than the weld into a cell has no box there. Low and far model files leave the boxes out; placement always reads the standard file. Boxes are tested only where two columns overlap, and a placement is refused only where a held part's box and a placed part's box overlap, outside the mate zones that excuse a mated pair; the refusal names that placed part ("<held> would overlap <part>'s bounds in <model> at cell x, z"). So boxes never refuse what the columns allow, and two meshes can interpenetrate by at most 0.1 LDU (the weld on each of two faces) before their boxes meet. They still refuse some physically possible arrangements, most of them involving parts turned off the 90° grid.
- Track pieces use `TrackPose`. A track piece whose pose lands on the lattice (only the ζ⁰ and ζ^(n/4) coefficients are non-zero, and both are whole numbers of studs) may also claim stud support.
- *Track seating:* off-grid angles come only through connections (§2). A run drawn on open ground starts on the anchor's stud corner facing the nearest quarter turn, and a held piece on open ground turns in quarter turns. A piece with two lattice ends (straight, switch, crossing) always lands with its body on the lattice: held by a lattice end, that end sits at the cursor; held by an off-lattice end (a switch's branch), the body takes the nearest quarter turn and stud corner and the end lands within half a stud diagonal of the cursor. A curve has one lattice end, so the held end sits at the cursor. Exact poses map to floats through the reduced basis (c₀ + (c₁ − c₇)cos π/8 + (c₂ − c₆)/√2 + (c₃ − c₅)sin π/8, and likewise for z), so a lattice pose is exactly whole studs at every heading and distance and a quarter turn maps (x, z) to exactly (−z, x).

### 5.3 Exact track arithmetic
This comes from connection rules §4.3, generalized for D3.
- Positions live in ℤ[ζ_N] with N = 16 today. Each position is stored as N/2 integer coefficients in studs, and each heading as k ∈ ℤ_N.
- A straight adds 16·ζᵏ. An R40 curve adds the exact arc chord in the field.
- Two track ends **join if and only if their coefficient vectors are identical and their headings differ by N/2.** There is no epsilon.
- When a layout mixes N = 16 and N = 32, poses embed into ℤ[ζ₃₂] through ζ₁₆ = ζ₃₂², so adding fan track later doesn't migrate existing layouts.
- Parts whose poses fall outside the field get an exact algebraic pose from their data, compared with ε = 1e-6 LDU to absorb representation error only. Some switches may fall in this group, and flex track would (unscheduled, §13).
- **Importing poses from LDraw decimals (project decision, delegated by the owner, 2026-11-16).** LDraw prints connector poses with 3 to 6 decimals, so a pose read from a file is identified with a field element when its residual to the unique ℤ[ζ₁₆] candidate is ≤ 0.0005 LDU per coordinate, half the last decimal of 3-decimal data. The candidate must be the only one in the search box (|c₀|, |c₄| ≤ 64 and |cₖ ± c₈₋ₖ| ≤ 64) within the file's printed precision. This is a data-identification tolerance used once, at import. It isn't physical slack and isn't the join ε: joins still compare the exact coefficients.
  - **Read per coordinate (approved 2026-11-18).** The rule says a pose "is identified with a field element when its residual to the unique ℤ[ζ₁₆] candidate is ≤ 0.0005 LDU, half the last decimal of 3-decimal data". Its stated basis is a bound on rounding each printed coordinate. So the residual is read per coordinate, the L∞ norm: every coordinate is within 0.0005 LDU. This matches how connector origins and axes are identified one component at a time (connector-engine plan §2.3). The field search (`findZeta16Representation`) and the track catalog's `residualLdu` report this per-coordinate residual, so the recorded number is the one the rule compares.
  - **At the limit (owner decision, 2026-11-18).** A sixteenth printed to three decimals (x.0625 as x.063) is exactly 0.0005 off, so it sits on the inclusive limit and identifies. In double precision the deviation lands a hair on either side depending on magnitude: 20.063 came out under the limit, while 0.063 and 100.063 came out at 0.0005000000000000004. That made the outcome arbitrary.
    - **Part-local identification** compares the parsed decimals exactly, in rational arithmetic, wherever they're available. Where the compared value is a Float64 product instead, it takes the same guard as model-frame identification. The pipeline's track-end certification compares the field search's residual, and the MILS rail lattice check compares `ldrawPlacement` output.
    - **Model-frame identification** compares against 0.0005 plus a 1e-9 LDU representation guard (`IDENTIFICATION_REPRESENTATION_GUARD_LDU`, combined as `IDENTIFICATION_ACCEPTED_DEVIATION_LDU` in `@brr/math`), because its values come from Float64 matrix products. The guard sits beside the join ε (1e-6) and, like it, absorbs representation error only and is never physical slack. It's six orders of magnitude below the residual.
    - Native and WASM builds give the same result at the limit, and tests pin that.
  - **Rail heads at track ends (owner decision, 2026-11-18).** The same 0.0005 LDU residual identifies each track end's rail head bands to a measured rail. The bands are measured on the end face along the end's identified normal. Official rail heads end in a half-lap, so the face carries only half of each head; the face's bands are closed with their image under the joint's half-turn about the vertical through the connector (negated lateral offsets), which is what a mating end of the same kind supplies, and must merge to exactly two bands. A band and its half-turn partner merge when they overlap or their gap is within the same 0.0005 LDU residual, because the seam ends are band ends identified like the outer ones. All four band ends must then lie within the residual of the unique `geometry.json` `rails[]` entry. Only connectors whose pose is certified (`status` is `certified` and `residualLdu` ≤ 0.0005) are identified; the rest record no rail and are reported as "pose not certified". The result is recorded per connector, once, at the pipeline and import boundary. Exact equality can't work here: curve ends sit at odd multiples of 11.25° and LDraw prints their vertices as rounded decimals. The two measured rails' bands are 0.475 LDU apart, so the candidate is unique. This isn't a join or contact tolerance: wheel-on-rail contact compares exactly with the `rails[]` decimals. An end that identifies to no rail (32087's 7 LDU heads) is reported and left out of rail-fit checks.
  - **Top-surface coverage (owner decision, 2026-11-20).** The same 0.0005 LDU residual, read per coordinate, is the third use of the same boundary. It decides one thing in a part's baked `topSurface` (`docs/part-bundle.md`): whether a cell's square is covered by the faces lying wholly at the part's top. A cell is covered when every point of its square lies within the residual of one of those faces, decided exactly by growing each face by the residual box and subtracting it from the square.
    - **Why:** LDraw prints four decimals, so the shared edges of printed art faces miss each other by 0.0001 to 0.0003 LDU. Read strictly, those slivers leave cells of printed road baseplates and printed tiles uncovered, so their road would have holes.
    - **It moves nothing.** No vertex, height or stud is changed. The top height, the stud bases, the pockets and the face pruning stay exact. The residual only decides whether rounding slivers count as covered, and an opening with any point farther than 0.0005 LDU from every top face can't count, so no slope cell, round-tile edge or real hole is covered by it.
    - **Measured on the full pinned library:** it covers 848 cells in 138 parts that strict coverage leaves open, and changes no other cell. 124 of those parts are printed variants, among them the road baseplates 44342p01, 44343p02, 2359p04, 2361p02, 2361p03, 609p01, 309p01 and 6099p01 to p07. The rest are stickers, the obsolete printed landing pad 80256 and 32277; the round clock tile 67095p01 gains only its centre cell, which lies wholly inside its circle.
    - The constant is the identification rule's own (`IDENTIFY_TEN_THOUSANDTHS` over `TEN_THOUSANDTHS_PER_LDU` in `brick-compile`'s `identify.rs`), not a new number. It isn't a join or contact tolerance.
    - **Wider print gaps are read from beneath, never by widening the residual.** Some prints scale up primitives whose rounded decimals disagree, or turn them by rounded matrices, and set them side by side, so their faces miss each other by 0.001 to 0.017 LDU (44343p02 and 613p01). The residual stays 0.0005. A part of the square that no top face covers counts as covered only when it is a crack in the part's top: top faces lie over the cell, nothing rises to the top along the gap, and the part's own undersides lie straight below it, read exactly from the faces beneath (`docs/part-bundle.md`, *Top surfaces*). That reading has no tolerance: a slot, recess, hole or step stays open however narrow it is. On the full pinned library it covers 408 more cells in 50 parts and changes no other cell. The gaps are print seams (at most 0.39 square LDU in a cell), triangles a print leaves out (4478p02, 3867p01 and 3867p02, up to 2.25 square LDU), and the ring under each of 109373's hollow studs, whose walls are drawn with the stud. Of the 8,624 printed parts whose plain part is pinned, 43 more now read the same top surface as it, and none that did reads differently.
  - **OMR authoring identification (pipeline boundary only; owner decision, 2026-11-19).** Official OMR model files have one more data identification, at the pipeline boundary only, behind an option the import worker never sets. Each type-1 position coordinate of a line whose own rotation is an exact signed permutation is identified once, in its parent frame, from its printed decimals in exact arithmetic.
    - It first takes the 0.0005 sixteenth step above.
    - Otherwise it identifies to whole LDU within r₁ = 0.05 LDU.
    - Otherwise, if it's printed with two or more decimals, it identifies to the coarsest ½, ¼, ⅛ or 1/16 grid within its print-rounding bound: half its last printed decimal, inclusive, and never below 0.0005. A grid is used only when that bound is below half its spacing.
    - At most one grid can apply, so the order doesn't matter: a coordinate within r₁ of an integer and within the bound of a non-integer grid point would need r₁ ≥ 1/16 − 0.005 = 0.0575. Moving parts relative to each other this way is accepted as dust removal and recorded per coordinate. Every other coordinate stays as authored, off-lattice and reported, never snapped or compared with any ε. User imports keep 0.0005. It's never a join tolerance: joins then compare the identified sixteenths exactly.
    - **Exact decimals:** it compares the printed decimals exactly, so the 1e-9 model-frame guard doesn't apply.
    - **The gate:** an explicit bake option, off by default and set only by the asset pipeline's compile of `.cache/omr` model records. A test pins that the import worker leaves it off.
    - **The named divergence:** re-importing an OMR `.mpd` through the import worker keeps 0.0005, so it differs from its bundle record wherever the rule identified something.
    - **Provenance per coordinate:** the printed text, the grid identified to, the exact residual, and the rule version. Per model: the rotated lines excluded, and a row for every coordinate not already on the 0.0005 step, including every coordinate left off-lattice. Counts per grid and the residual distribution are derived from those rows, not stored.
    - **Measured basis:**
      - TotalyWicked dust off whole LDU runs from 0.01 to 0.11 with no gap before the eighth cluster.
      - Against the sixteenth grid, distance is bounded by 1/32, so rounding there isn't identification.
      - In the 18 OMR builds, this rule (signed-permutation lines, r₁ = 0.05, fine grids only for two or more printed decimals) gives +2,245 joints and 0 lost, and 4,738 mate rows, 1,931 of them relative, with a maximum relative shift of 0.100 LDU. It forms 4 bogie and 18 coupler pivots (from 0 and 3), and changes clean sets only in 10218-1 and 10264-1, each explained.
      - The 33 one-decimal coordinates no longer reach fine grids. That removes 19 joints (73 mate rows, all but one between parts sharing one offset) and no pivot.
- **Identifying placed track in an imported model** (`modelTrackEnds`) applies that rule to every catalog track piece. It reads only the Float64 part transforms, never the Float32 render copy.
  - **Why not each end directly:** the search box holds about 1,049 candidates within 0.0005 LDU of a point, so no end's float position has a unique candidate on its own. Uniqueness is obtained in the steps below.
  - **Rotation, per printed entry:**
    - The heading is certified like an axis code. Each of the four plan rotation entries must lie within 0.0005 of the exact cos or sin of θ = k·22.5° plus the profile's half step (the part frame's heading offset), for one k ∈ ℤ₁₆.
    - Headings 22.5° apart differ by 0.39 in (cos θ, sin θ), and so by at least 0.27 in one entry, so the certified heading is unique.
    - A shear, a scale, a mirror or an angle off the ζ₁₆ steps doesn't certify, and the piece is `overLimit`.
    - Ends are then composed from the exact ζ₁₆ rotation, so the printed rotation decimals never multiply a connector's distance from the part origin. The residual measures the translation only. The placement is read from the translation with ζ₁₆ᵏ applied exactly.
  - **Seat (stud seating):**
    - A piece whose certified heading is a quarter turn, and whose placement is within 0.0005 per coordinate of a lattice pose (`isLatticePose16`: whole-stud x and z, quarter-turn heading), is anchored on that pose.
    - An axis-aligned track piece on a baseplate is on the lattice through its stud mates. Lattice poses are 20 LDU apart, so the seat is unique.
  - **Window anchor:** any other piece's placement offset from the nearest whole-stud point must be the only candidate in the search box within 1e-6 LDU on each axis. The stud lattice is an exact symmetry of the field, so the whole-stud shift lifts the box's limit on c₀ and c₄ without loosening uniqueness.
    - Two candidates in the box differ by an element whose coefficients lie within twice the box (128). The smallest nonzero such element is 3.86e-6 LDU on its larger axis, more than the window's 2e-6 LDU diameter, so the window never holds two candidates. A math test pins this.
    - This uniqueness covers only offsets inside the box. An offset always lies within a stud of the lattice, but its coefficients grow with every turned piece between it and a whole-stud point. In a 1,020-piece test layout they reach 208, and about half the offsets fall outside the box. For such a piece the search finds no candidate, or rarely a stray one.
    - A window candidate is only as good as the translation's printed precision. A 3-decimal translation lies up to 5e-4 LDU from its true offset, and about 0.5% of such points have an unrelated candidate inside the window. Before the rule below, a layout with 3-decimal translations had 21 of 1,020 pieces identified at exact but wrong poses.
  - **One embedding per run:**
    - Seats anchor first, then window anchors. Each anchor spreads through joins, and every anchor in the reached run votes for the shift between its own pose and the propagated one.
    - A shift is corroborated by a seat, or by at least two agreeing window anchors; correct anchors agree with each other, and strays don't. The run takes the corroborated shift with the most votes.
    - No corroborated shift leaves the run `noAnchor`. A tie is a contradiction.
    - Every other vote implies a rival embedding of the run. A piece whose data passes 0.0005 under both embeddings has two field candidates, and is a contradiction.
    - So a quarter-turn straight at the box element 3.59e-5 LDU from a stud point is never seated silently: if a neighbour's own anchor implies that true pose, the straight is a contradiction.
  - **End consistency:** a placement is accepted only if every composed end is within 0.0005 LDU of its exact ζ₁₆ end in each coordinate. Neighbour lookup searches twice that distance, because two float ends of one exact end can each be 0.0005 off. Acceptance still compares each float end with the exact end.
  - **Propagation:** a piece whose float end meets a certified exact end with the opposite heading takes the placement that end implies through `attachPose16`. Exactness follows the joins, so a piece whose offset leaves the box is identified only through them, however large its coefficients grow.
  - **Contradictions are off-field:** a piece whose passing candidates disagree is reported, never snapped and never joined. Its candidates can come from different neighbours, from a neighbour and its own anchor, or from rival embeddings. A loop that closes only approximately is reported this way, not forced shut.
  - **Every unidentified piece is reported with a reason:**
    - `notFlat`: it isn't flat, or it sits between plates.
    - `noAnchor`: nothing gave it a candidate. Neither its own anchor nor a certified neighbour did, and no certified neighbour's end faces one of its ends within the near-miss radius.
    - `overLimit`: its rotation doesn't certify, a candidate missed 0.0005, or one of its ends misses a certified neighbour's.
    - `contradiction`: two field candidates within 0.0005 LDU.
    - The editor counts `noAnchor` pieces separately from off-field ones.
  - **Printed precision of real files:**
    - Files that print 6 decimals are identified completely.
    - At 3 decimals, every run with an axis-aligned piece on the lattice is identified: the R40 circle 16 of 16, and a quarter-turned 117-piece set 117 of 117.
    - **Known limit:** a run turned off the quarter turns as a whole has no seat.
      - At 3 or 4 decimals it has no window anchor either, so it isn't identified on the field. At 5 decimals that happens only when two window anchors happen to agree: one 33-piece arrangement of the 117-piece set, and none of the 22 such runs in the 1,020-piece layout. At 6 decimals it is identified.
      - Below that, it is identified in a run frame (next bullet), not on the field.
    - No piece is identified at a wrong pose in any of these cases.
- **Run frames: unanchored runs identified up to one shared translation.**
  - **The idea:** inside one imported model, a run's relative poses are exact compositions of certified profile vectors, given the certified headings and which ends join. So the run is identified up to one unknown translation t. That is the same structure the absolute rule has, minus the anchor.
  - **Who takes part:** every piece whose only failure is the anchor. That means `noAnchor` pieces, and pieces labelled `overLimit` only because an end misses a certified neighbour's within the near-miss radius. Never a contradiction, a rotation that doesn't certify, or a piece whose own candidate missed 0.0005.
  - **Joins:**
    - Two such pieces join when their float ends are within the neighbour lookup's reach, on the same plates, with exact headings half a turn apart.
    - An end with two partners, which a duplicated piece gives, makes every piece involved a contradiction.
    - Relative poses spread breadth-first through `attachPose16` from a root at the origin. A piece reached twice with different exact poses (a loop that doesn't close exactly) makes the run a contradiction.
  - **The test:**
    - Per coordinate, t must lie in the intersection over pieces of [fᵢ − Δᵢ − 0.0005 LDU, fᵢ − Δᵢ + 0.0005 LDU]. Here fᵢ is the float placement and Δᵢ the exact relative position. With exact rotations, an end's residual equals its placement's residual.
    - An empty intersection makes the run a contradiction, and a run needs at least one internal join.
    - This is the per-coordinate rule applied to the run as a whole. There is no new tolerance, and no field search, so there's no density problem: the joins fix the relations combinatorially.
  - **What the run frame is:** exact relative `Pose16`s and a float centre t̂ of the interval. Joined runs pass or fail as a whole; nothing is split to make one pass. Runs that come near without joining keep separate frames, and their gap is reported as a near-miss gap.
  - **Track graph:**
    - Each placed run gets a frame id, and `TrackLayout`, `TrackGraph` and `TrackEnd` carry it. Join keys include the frame, so ends join only inside one frame.
    - A run-frame end never joins world track or another run frame, even at the same exact pose.
    - `ModelConnectors` refuses a run-frame end, so it can't join another model's track either.
    - Drawn track can't attach to a run-frame end.
  - **Play and views:**
    - Play and the views use the float placement: the model's exact lattice frame, then t̂ rotated by the model's quarter turn, then the exact relative pose.
    - A train runs on a run frame's own graph, closed loops included.
    - No absolute ℤ[ζ₁₆] pose is ever claimed for run-frame track. If a later rule anchors one of its pieces, the run becomes absolute through the existing propagation.
  - **Validity:**
    - A run frame's internal joins satisfy the track rule (ends join exactly), so a closed run frame with no open ends counts toward Valid.
    - Its open ends are ordinary open-end errors unless capped by a buffer or marked open by the user, because no external join is possible.
    - All other rules apply unchanged. Run-frame track never claims stud support: off-lattice track must rest on flat support.
  - **Panel:** the editor counts model pieces on the field, in a run frame, and off the field or unanchored, on three rows.
- Every track part's connector poses are **imported from data and tested against the field at build time. Nothing is hand-coded.**

### 5.4 Profiles
`TrackProfile` holds the system, gauge class, angle step N, minimum radius, parallel spacing, clearance envelope and flags.

`ModuleProfile` holds module size, surface height in plates, edge connector slots, track centre from the edge, sidewalk depth, lane width, and ballast width and height.

Each `ModuleProfile` also carries a **substructure recipe**: the parts needed under one module (for MILS, the raising bricks, cover plates and Technic join bricks, per 32×32). The plan BOM includes these parts, so "buildable as planned" counts the hidden parts too.

The MVP ships four module profiles: `free`, `lego-modular`, `mils` and `club-road`. Numbers are filled in only once their verification item in §11 is cleared; until then a profile's rules show as "unverified" warnings. The cleared numbers, with sources, are in `docs/verified-facts.md` (Module standards):

- **`mils`** is MILS core only, as published in HispaBrick Magazine I–IX. It has 32×32 modules with the ground 4 plates above the baseplate (edge tolerance one plate). Each corner keeps a free 2×2, then a 1×4 Technic brick along each adjoining edge (8 per module). Paved roads are 16 studs wide, centred, with the surface at 5 plates. Paths are 4 studs and earth tracks 8 studs, both at 4 plates. Rivers are 8 studs, with water at 2 plates. Road and river curves are single 90° elements. The substructure recipe is the published minimal module: a 32×32 baseplate, 4 bricks 2×2, 8 Technic bricks 1×4, 8 bricks 2×4 and 4 plates 16×16 (25 parts).
- **`club-road`** is separate from `mils`, not a parameter of it, because club road systems are incompatible with MILS roads and with each other. Its defaults are L-Gauge MultiRoad: streets at 6 plates and walkways at 8 plates above the baseplate, against 5 plates for a MILS paved road. The sidewalk width is set per club (4, 5 or 6 studs are all in use), and there's no shared standard.
- **`lego-modular`** has a 32×32 footprint, joined by 1×2 Technic bricks on the first course at stud cells 9–10 and 21–22 of each joining edge, as modelled in the LEGO modular-building OMR files. Sidewalk depth isn't standardised. Its joins don't line up with MILS's corner joins, so mixing the two needs an adapter rule.
- **Track on modules:** MILS publishes no City or Train rules and no ballast standard, so track on `mils` modules needs a project decision. The one firm convention is 16-stud spacing between parallel track centres, which the 9V switch plus a reversed R40 curve gives exactly. *Decision (2026-11-17):* the rail module template is the basic terrain module with one pair of 9V straights centred on two opposite edges, on the 4-plate surface without ballast, and is labelled a project rule, not MILS. R40 curves don't fit a 32×32 module, so there's no rail curve template. As on MILS train modules built from 16-stud track sections (S18 in `docs/verified-facts.md`), the track's connectors sit exactly on the centres of the two rail edges, laid from the exact ℤ[ζ₁₆] piece poses onto integer LDU. The 9V end tongue reaches 9 LDU past the edge: it's part of the track end, a declared connector under §7.2 rule 4, and the owner's decision of 2026-11-17 lets a track piece's end tongue overhang a baseplate edge or a seam.
- **Module templates:** the palette's MILS modules are generated by `tools/asset-pipeline/src/mils/mils-modules.ts` from `mils-profile.json`: basic terrain, paved road straight, curve, T-junction and crossroads, earth track and path straight and curve, river straight and curve, and the rail module. Every edge is checked against the feature widths and heights above when the template is written. In the editor the templates are listed and placed like any other model and keep their credits. There is no module grid, edge classification, rail-edge refusal or track-tongue space. Only resting and the slab still read the bundle's `role: "mils-module"`: a template rests on the top of its own baseplate and keeps the slab below it, until one table plane replaces that branch for every model (`docs/connector-engine-plan.md` §2.5, E10). Module joins come back from real stud, anti-stud and Technic mates for any model (E6), and MILS road and river continuity comes back as an advisory check on the sampled edges of any model.

**Road plates.** The current LEGO road system (set 60304 and later) is official in LDraw as 69958 (16×16) and 71772/71772p01 (8×16). These are 2-plate-thick plates, not 32×32 baseplates. Their studs stand in pockets 1 plate below the top face, lane markings are separate 2×4 tiles laid in those pockets, and there are no clips. A 32×32 road chunk is four 69958s. The road layer therefore needs a "plates plus inlay tiles" model, and the stud-occupancy grid must handle studs below the top face. The classic 32×32 road baseplates stay supported.

**Drawing track along a stroke.** A track drag records the pointer path and lays track along it. The run starts at the open end under the press, or, on open ground, at the stud under the press, facing the quarter turn nearest the stroke's direction over its first half straight. Pieces are laid one at a time from that end: at each step the editor picks the drawing kit's straight, left curve or right curve whose exit, looking three pieces ahead, keeps closest to the stroke in position and heading. It stops when less than half the next piece is left of the stroke, and never lays more than the stroke's length plus one piece. Which piece comes next is a UI choice; every join stays exact. A piece that would overlap placed track it doesn't join, an earlier piece of the same run, or what the placed geometry offers it (the same geometry test as a closure, below) is drawn red and not laid: the run stops before it, and the hint bar names what it would hit, before and after release.

**Drawing track to an open end.** When a drag ends on an open end, the editor suggests only a closure that joins it exactly and crosses nothing, or nothing at all. It follows the stroke as above, then joins from the run's end, or from up to four pieces back along it, with the cheapest valid run of up to three turns that is no longer than what is left of the stroke plus two pieces. If none fits, it falls back to a closure from the start end alone, chosen as follows. A closure is valid when no piece overlaps placed track at the same height, another piece of the same closure, or what the placed geometry offers it. That is read from geometry alone, the same way for a loose baseplate or road plate, a MILS module or a set, and never from what kind of thing a placement is: any measured part box that reaches into the track's height band is solid, and any part whose top face is the plane the track rests on must carry a stud, at that plane, under every stud cell the piece covers. So a baseplate's studs seat track, a road plate's roadway (which has no studs) refuses it while its sidewalk studs seat it, and a road plate inside a set is judged by exactly the boxes and studs it has there. Open ground, where nothing has its top face at that plane, is the sandbox table and stays free. Each piece's plan outline is the convex hull of its own mesh, which the pipeline bakes into the bundle's `trackShapes` (editing code never reads a mesh), placed at its exact pose; boxes that only touch don't overlap. The only overlap excused is the part of a piece that lies inside the outline of the piece it joins: the joined piece itself, and whatever already overlaps that piece there, such as the baseplate edge a 9V end tongue overhangs in the joint. Track an imported model carries is judged by these outlines like laid track, and its parts' boxes are not obstacles too. Among valid closures the editor prefers the fewest pieces, then the shortest centreline, then the fewest changes of direction: the exact algebraic minimum when it fits, else the cheapest valid run of up to three turns, else a bounded best-first search over exact poses. If none is found, the ghost is empty and release lays nothing ("blocked"), and the hint bar says what the shortest exact join would cross.

**Laying pieces from the library.** While the track tool continues from an end (the last end laid, until Esc lets go of it), choosing a track piece in the library lays it on that end exactly, attached by its first end, as one edit step. With no end being continued, the same choice picks the piece up to place by hand. The end then moves to the exit whose heading continues the entry's, read from the piece's own connectors: of its other ends, the one whose heading is the fewest ζ₁₆ steps from the entry's reversed, and the lowest-numbered on a tie. So a switch entered by its points continues along its straight route, and one entered by either route continues out of its points. If that exit joins another open end, no end is continued. The piece stays among the next-piece choices of every end and is previewed on the new one, so Enter lays it again with the same hand and Q turns it to attach by its next end. It's checked like the held piece dropped on that end and is laid level at that end's height, never as a ramp. Nothing reads what kind of piece it is.

**Dropping a piece into laid track.** A held piece over laid track at the drawing height, with no open end under the cursor, looks for the run under the cursor: up to four laid, level, two-ended pieces each way, joined end to end. It goes in where two of its own ends coincide exactly (`pose16Equals`) with the outer ends of a stretch of that run, and replaces that stretch: a 9V switch takes the place of two straights, a crossing of one. Its other ends stay open or join open ends exactly. Of the poses that fit, the one whose body centre is nearest the cursor is shown; Q and R step through the others, and X swaps the hand. The clearance check excuses the lifted pieces and counts the ends they leave open as joins, the same rule a moved selection uses, so the neighbours on both sides join. Track a user's model carries, track a train stands on and a piece over a copy of itself are never lifted. The click is one `TrackChange` that lifts the stretch and lays the piece ("Undo lay 1 piece in place of 2"). Nothing reads what kind of piece it is.

**Closing gaps.** In the track tool the editor offers every gap it can close exactly as one click. It considers the same pairs of open ends as the next-piece choices on an end: for each open end, the four nearest open ends ahead of it within 96 studs, laid track and a model's own track alike. Each pair is solved once, from the first of its ends that has the other ahead of it, by the same closure as a drag that ends on an open end, so an offer is exact, crosses nothing and is supported by the same geometry test, and a run between ends at different heights ramps as a run from an open end does or isn't offered. The search runs a slice of each frame, at least one pair a frame, nearest pairs first, and starts again whenever the open ends, the obstacles, the drawing kit or the ramp rate change; a drag pauses it. Solves are shared with the next-piece choices and drags through the same per-field cache. The panel lists each offer with the pieces it would lay and the two ends it joins; pointing at an offer shows its run as the ghost and marks its two ends, a click lays it, and O lays the nearest. Each close is one undo step.

**One edit history.** Every edit is one step in a single `EditHistory`: placing, rotating and deleting models, road strokes, track runs, held-piece clicks, library pieces laid on an end, loop closures and switch throws. A track step records the pieces it lifts and lays as index-addressed records of catalog piece, exact ℤ[ζ₁₆] pose and height (`TrackChange`). Undo lifts exactly the pieces the step laid and puts back any it lifted at their old indices, so the laid-track order, the joins (recomputed from the restored poses) and the saved records come back exactly; redo replays the step as made. A switch throw is a lift and a lay at the same index. Ctrl+Z and Ctrl+Shift+Z walk model and track steps in the order they happened, and the Undo and Redo buttons name the step ("Undo lay 20 pieces").

**Road surfaces (D3).** Every placeable, a single part or a whole model, gets its road surface from geometry alone, read from each part's baked `topSurface` (`docs/part-bundle.md`, *Top surfaces*). A cell's top is the highest box top over it, identified to a sixteenth of an LDU; a top that doesn't identify leaves the cell unread. Every instance whose box top equals that top may claim the cell from its own record, so file order never decides: the cell is road when one of them stands upright on a quarter turn with its top-surface grid on the cells and marks the cell flat with no stud standing on it, or when one marks it a pocket and its recessed stud is uncovered (no other part over the cell reaches above the stud's base, including a part that isn't flat standing flush at the top). A flat face at the top wins over a pocket. Stud positions are identified to sixteenths too, and a stud blocks every cell whose centre lies within a stud of it on both axes, so a jumper's stud blocks both cells it stands between; a stud whose position doesn't identify blocks every cell it might at its own height (its height identified on its own, or else every top within the identification residual of it), rather than guess. Road tops and stud bases are stored in sixteenths of an LDU, so parts at a fractional height inside a model join only road at the same fractional top. Every other owned cell records its top and any stud standing on it, and isn't road. A road cell's side is an open road edge only where a piece could be set against it: where its own placeable has nothing beside it, or a lower cell with a stud standing on it. A side against its own taller part, its own lower cell with no stud on top, or its own occupied column whose top doesn't identify (a minifigure) is closed, so it draws no outline and road snap slides along no run there. A side that meets another placement at another height stays open. A placeable with no road cell has no road surface. No role, kind, palette section, set or part number is read, so road inside a set or a user's imported file joins drawn road exactly as the bricks would. Rule 7 mismatches are reported by plan validation (`roadJoin`) and shown in the road readout, never refused at placement. The one road refusal is an overlap: the held piece's road cells, at the pose's own height, lying on placed road cells at the same top. A click, a fill, the assist, a move and a turn decide it at the pose they would place; road snap and the readout decide it at the pose they show, resting a candidate the way the ghost rests. They all use the same exact probe on whole cell squares, through an index of placed road. Road at another top, such as a car parked on a roadway or a plate stacked on a baseplate, and studded or other non-road cells are never an overlap.

**Road snap.** Physical joins decide first. Road snap runs only in assist mode, once the placement assist has settled on an accepted pose; it may replace that pose with a road-clean pose (a clean join, or a contact flush with a neighbour's corner), the one joining the most road cells and then the nearest, chosen among poses flush with each placed surface's sides and sliding along its open road runs, only when the solver accepts the new pose with at least as many joints. Road snap never moves a refused pose: a piece the solver refuses stays refused at the cursor, as the module-join acceptance requires. So a modular settled on its pins is never moved, while a road plate on studded ground, whose stud joints are the same at every lattice pose, snaps to the clean join. On hover it keeps the held turn; R lets it pick among the turns that fit, at the next settled pose. A snapped pose holds while the cursor stays on its stud. Precise mode never pulls or turns: the click is judged at the cursor. Moving or pasting a group follows the same mode and the same rule: it takes a road-snap offset only when the group is accepted at the cursor, the shifted group lays no road in placed road, the solver accepts it, and every member keeps at least the joints it had at the cursor.

**Drawing roads.** Road kits are derived from the bundle, never listed by hand. Every road surface has a cell map of top, stud base and road flag. Only single-part placeables form kits, because those are the pieces the tool can lay. A side whose edge cells include a road cell is an *arm*. Square, centred pieces whose arms all share one edge pattern (for example 6 + 20 road + 6 studs on the classic 6-stud plates) and one colour form a kit. A kit offers whichever of straight, curve, T-junction and crossroads its pieces cover, and the palette shows the missing shapes. A drag becomes a 4-connected path of kit tiles: on the grid of an existing compatible plate under the start of the drag, or on the 32-stud chunk grid. Consecutive tiles need an arm towards each other, and a tile also connects into any compatible open road end facing it. Each tile gets the piece and quarter turn whose arms match exactly, or the smallest superset (a lone tile or a dead end becomes a straight). An existing plate of the same family on the path is swapped for the piece with its old arms plus the new ones, so branching off a straight lays a T. A placement with exactly the tile's footprint at plate 0, no road cell, and a top flat at one height across its plan at the kit's own road top (its corner cells may be open, because baseplates round their corners) is swapped for the road piece, so a road can be drawn across a laid-out baseplate grid. Nothing else counts as ground: a model with any part box under a tile in plan refuses it as an overlap. Part boxes, not the model's whole box, decide, so the same bricks block a stroke alike whether they sit in one file or several. Every proposed piece is checked with the rule-7 join check: any mismatch, overlap or missing shape refuses the whole stroke with a reason per tile, and nothing is laid. A valid stroke is one undoable edit.

**Erasing roads.** In Erase, a drag lifts the active kit's plates under the stroke (never another family's). A junction left beside them becomes the smallest kit piece that covers its remaining arms and has fewer arms than before, exact matches first; if the kit has no such piece, or no arm is left, the junction stays and is reported. A plate laid over ground gives back exactly the ground piece that stroke swapped out (part, colour, pose), remembered per placement through later upgrades, undo and redo; a plate laid on an empty table is just lifted, so erasing never adds or recolours a part. The stroke is one undoable edit, and downgrades pass the same join check as drawing.

Third-party track arrives later as an extra `TrackProfile` plus a `PartSource` (§3.5).

## 6. Renderer

**Scene model.** The world is a **sparse, unbounded hash map of 32×32-stud chunks**, one per baseplate or MILS module, grouped into 8×8 super-chunks. Each chunk holds placements. The renderer draws **model instances**: a model placed 20 times is drawn instanced, and every track and road piece is instanced too.

**Streaming (D4).** The camera chooses a tier for each chunk. Near chunks load fully. Mid and far chunks load only their merged or voxel model meshes. Super-chunks beyond the far radius stay unloaded and show as a super-chunk far LOD, or as a flat ground color until that exists. Super-chunk shards load from IndexedDB on demand, so a world's total size doesn't affect frame time. Super-chunk far LOD was moved into M6, isn't built, and is frozen under D6.

**Camera-relative rendering (M1 S4).** World positions are exact integer LDU, up to the whole int32 range. float32 has a spacing of 2 LDU at 10 km, so no world-scale coordinate is sent to the GPU. The renderer keeps a render origin at a chunk corner: chunk groups are placed at (chunk origin − render origin) and the camera at (eye − render origin), with both differences taken in float64 from exact values. While the camera moves, the origin stays put until the eye is more than 8 chunks away, then moves to the eye's chunk. That's hysteresis, so an orbit rebases about as rarely as it did in S4. Once the eye has been still for 250 ms, the origin moves to the eye's chunk if it isn't there already (S9). A camera at rest therefore always renders from the same origin, and a reload from a saved camera draws the same pixels however the camera got there. Each move is logged with its frame number; the log keeps the last 256, and the HUD counts them all.

**Plan overlay.** Plan regions draw their room walls, table tops (with their real heights as optional plinths), obstacles, aisles and reach zones as translucent overlays, with mm/cm/inch rulers. An optional "real table" view hides everything outside the region.

**2D plan backend (D6; built in B2).** The default editing surface is a top-down, north-up, orthographic plan drawn by its own backend, `PlanSceneBackend` in `render`. It sits behind its own interface and typed token, not `ISceneBackend`, whose calls are about part meshes, LOD tiers and a perspective eye. It takes the same overlay inputs (plan overlays, markers, track ends, guides, selection and issue boxes), so the client's overlay code feeds either backend.
- **Glyphs from geometry.** Each part and model gets a top-view glyph: a coverage-and-colour raster at a fixed number of pixels per stud, plus an outline, baked from its standard-LOD triangles by `brick-compile` with integer rasterisation. Like every bake, it is byte-identical natively and in WASM, proven by a parity test like `library-bake-parity` (B2.1). The pipeline bakes glyphs for palette parts, models and the library bake, pinned by the manifest (B2.2). The import worker bakes them for a user's file, custom parts included, cached by content hash (B2.3). The glyph schema lives in `@brr/schema/bundle`. This is BlueBrick's hand-drawn sprite library, generated for every part and every imported file. Glyphs keep alpha, so transparent parts read as transparent, and the selection draws the footprint outline separately, so an overhang can't hide what a model stands on.
- **Presentation only.** Placing, joining and checking never read a glyph. They read connectors, footprints and part boxes, exactly as in 3D. A pick radius in 2D only chooses which open end or candidate to preview; the pose is exact or refused with a reason.
- **What it draws.** Chunked, instanced, unlit glyph quads from typed-array instance pages. Baseplates draw as their colour, with stud dots once zoomed in. Laid track draws as its plan outline from the bundle's `trackShapes` plus its centreline from its track routes. Colour modes tint everything by layer, contributor, track system and radius, or height (B2.9). It also draws tables, the room, obstacles and aisles; zones, text, rulers and the legend; and the overlays: open ends, joins, the ghost tinted with its reason, selection, height labels and issue markers. A level filter dims and locks other height bands, so a two-level plan stays editable. `client` adapts domain data into its buffers, as it does for the 3D backend, because `render` may not import `domain`.
- **Mesh-free start (B2.8).** The editor is ready once glyphs and connector records have loaded. GLBs stream only for the 3D view or a 3D ghost.
- **One document, two views (B2.7).** The view camera's `plan` mode, which P toggles, drives the 2D backend, and the orthographic 3D plan view (under *Look* below) gives way to it. A split view shows both, and every edit in one shows in the other. Navigation zooms at the cursor with a capped step and pans by trackpad, Space+drag and the minimap. Display grids at 1, 8, 32 and 96 studs carry cell indices (A1, B2, …); like the ground's lines, they are display only, and nothing snaps to them.
- **Budgets** (Tier A, on the show-scale world in §13): pan and zoom at 60 fps with main-thread JavaScript ≤ 6 ms a frame, and ≤ 1 GB for a 2D-only session.

**LOD per model**, chosen by screen size:
| Tier | Geometry | Studs |
|---|---|---|
| Near | Per-part instancing (one `InstancedMesh` per part per 32×32 chunk, chosen in M0 over `BatchedMesh`; see §11 item 9), LOD0 or LOD1 parts | Instanced stud stream, covered studs removed |
| Mid | Merged model mesh built from LOD1 or LOD2 parts | 8-segment studs without logo, or a normal map |
| Far | Voxel greedy mesh of the model (1 stud × 1 stud × 1 plate) | A procedural pattern computed from `worldPos mod 20` |
| Very far (not built; frozen under D6) | Voxel greedy mesh of the whole super-chunk, then impostors | none |

*M0 status (2026-11-16, slice 3):* the city picks a tier for each 32×32 chunk every frame from the projected stud pitch (near ≥ 12 px, mid ≥ 3 px, else far). Near draws the standard parts and the standard stud stream. Mid and far draw a far LOD instead of merged or voxel meshes: the `p/8` part triangles minus those the part itself appears to hide from above.

The far-LOD visibility test is sampled, not exact. A triangle is kept if any of 7 points on it (the centroid, plus points near each vertex and each edge midpoint) has an unblocked ray, on either face side, along any of 1,024 upper-hemisphere directions or a 64-direction horizontal ring, cast against the part's own triangles. An independent dense re-check (7 points, 512 + 64 directions) finds:
- 3001, 2412b and the other city bricks, plates and tiles: no visible dropped triangle;
- 3062b: nothing dropped;
- 53401: 1 visible triangle out of 1,203 dropped, covering 8 of 51,081 LDU² through 0.17% of directions.

The earlier 64-centroid-ray version dropped 122 visible 53401 triangles and all of 3062b's 60. "Above" means the part's own +Y, so the far LOD is valid only for upright parts. Mid adds 8-segment studs, and far drops studs. The M0 city also culled covered studs per chunk by part role; that path was deleted with the city on 2026-11-18, and covered studs now come only from each model's baked stud cover and the footprint rule below. The super-chunk meshes and impostors aren't built yet.

*M1 S7 status (2026-11-16):* baked models tier like city chunks. Near is unchanged. Mid draws the far-LOD shells for upright instances and the full part mesh for any instance whose own +Y isn't world +Y, because the self-hidden test only holds for upright parts. Far draws the model's voxel greedy mesh instead of its parts. The far bundle carries one `model-<name>-far.glb` per model. Its mesh has one primitive per LDraw colour, and its extras hold the voxel grid (`origin`, `dims`, `cellLdu` [20, 8, 20]) with two uint32 accessors, `voxelCells` (x + dims[0]·(y + dims[1]·z)) and `voxelColors`. The grid phase comes from the model's lattice, the same rule placement uses (`lattice.rs`). A cell is occupied if any standard-LOD body triangle (studs excluded) meets the cell's box, shrunk by 0.1 LDU on every side, over a positive area. Its colour is the one with the largest clipped area, opaque colours first; areas within 1e-6 LDU² of each other count as a tie, and the lowest colour code wins. Chunks mark the part instances a voxel mesh replaces with `ChunkInstances.voxelized`. `ISceneBackend.setFarModel` registers each placed model's voxel mesh along with every chunk its parts landed in. The mesh shows whenever any of those chunks is far, so a model split across chunks never has a hole. The only overlap is a voxel mesh over mid shells at about 3 px stud pitch: a model spans under 700 LDU, so its chunks can't be near and far at once. A model whose bake finds no lattice, or whose phasing layer (S5) isn't on a whole LDU, gets `farMesh: null`, and viewers draw it with no far model, so its far chunks draw the parts' shells. The pipeline's build output names which of the two applies, with the layer's y for the second. A model's `notDrawn` sections never reach its far mesh. Each far GLB carries `extras.ldraw` (the model's file, source, section authors and licenses, a modified-from-LDraw note describing the voxelization, and every LDraw file that shaped it), and the far bundle's credits include those files. `?tier=near|mid|far` forces a tier, and in the editor L cycles it.

**Studs.**
- Studs inside a model are culled when the model is baked.
- Baseplate and road-plate studs under a placed model's base footprint are culled at placement time, using a per-chunk occupancy grid.
- We never draw a logo.

*M1 S6 status:* a stud is culled at bake when two tests pass.
- **Enclosed from above:** one other opaque part of the same model has its bottom plane at the stud's base (same up direction, within the compiler's 0.05 LDU weld tolerance) and encloses the stud's volume. The test probes the stud's axis and four points at 0.9 of its radius, at half its height; the stud's height and radius come from the compiled stud primitives. From each probe, rays at the zenith and at elevations 0°, 30° and 60° in 16 azimuths (every 22.5°, so including the lattice axes and diagonals) must all hit that part's opaque standard-LOD triangles.
- **Closed below:** from points just outside the stud's surface at 8 heights ((k + ½)/8 of its height), rays every 2.5° from −2.5° to −90°, along the stud's own 64 azimuths and the model's 64 lattice-axis azimuths, must each hit opaque geometry of any part of the model within 3 studs (60 LDU). This keeps the edge studs under an overhang, which are visible from below through the open underside.

A triangle whose resolved colour has an LDConfig `ALPHA` below 255 neither covers nor blocks. The model's visible studs ship as a bitset in the model file, and the editor and `?model=` viewer (`view=below` orbits under the model) drop culled studs before building the stud stream. A footprint cell is a lattice cell at the model's lowest vertex where a hypothetical upright stud would be enclosed from above. It is *flat* when a ray straight down from the probe also hits the part (a solid bottom, such as a modular's own baseplate), and *anti-stud* otherwise. At placement, a stud of any placed thing (a baseplate, or a lower model's roof) is dropped when its integer cell lies in another placement's footprint and its integer base height equals that placement's rest plane in LDU. Under an anti-stud cell, all 8 neighbouring cells must also be closed at that height by another placement's column; otherwise the stud could show from below. Off-lattice or non-upright studs are never dropped.

**Look.**
- A plastic material: roughness about 0.25, a clearcoat lobe and calibrated LDConfig colors.
- IBL lighting, SSAO or GTAO, and an outline pass driven by instance id, normal and depth (the default).
- A bevel-normal shader trick for rounded edges, plus optional baked bevels on LOD0.
- One cascaded shadow map rendered from the mid tier.
- Weighted blended OIT for transparent parts.
- Optional instruction-style edge lines on the near tier.

*M1 status (S8):* every item above except the baked LOD0 bevels and the instruction-style lines is in `render`, each toggled by the viewer's `look=` parameter (`plastic`, `gtao`, `outlines`, `bevel`, `shadows`, `oit`; `all`, `none` for M0's lighting and material, a list, or `-name` to drop one from `all`).
- **Transparency in every mode, including `none`:** LDConfig colours with `ALPHA` below 255 get their own instanced meshes and materials and blend. This is a correctness fix: M0 drew them opaque. So `none` matches M0 pixel for pixel only where nothing is transparent.
- **Defaults** follow the M1 rule that a pass is on by default only if 250k aerial stays under 16.7 ms on the M4 Max with it. Measured at `50c281b` (median ms, WebGPU / WebGL2, a loaded machine): `plastic` 14.9 / 15.2 and `plastic,outlines,bevel` 14.7 / 15.3 are on; `gtao` 22.8 / 15.3, `shadows` 22.5 / 18.1 and `oit` 17.5 / 15.1 are off. Without OIT, transparent parts use three's sorted alpha blending.
- **Material and light:** roughness 0.25 for the diffuse base with its specular turned off, and the ABS surface reflection as a single clearcoat lobe (strength 1, roughness 0.08). A specular lobe at the base roughness spread the sun's reflection into a wide glare that washed flat track and plates near white wherever the camera sat near the mirror angle. The scene is lit by a sun, a diffuse-only hemisphere fill and a procedural sky dome as IBL. Intensities are calibrated so an exposed top face renders close to its LDConfig sRGB value.
- **Post:** the scene pass is single-sampled with a G-buffer of RGBA8 normals and RG16F ids, and FXAA runs last on both APIs. GTAO at CSS-pixel resolution multiplies the scene colour. Outlines come from an id, normal and depth G-buffer: silhouettes where the neighbour lies behind and off the centre pixel's tangent plane, seams between different parts on one surface, and concave creases. The bevel trick shades convex creases with the averaged normal of the two faces. Edges fade with the projected stud pitch.
- **Shadows:** one sun `CSMShadowNode` (3 cascades, 2048²). Casters live on their own layer. In tiered scenes each chunk casts from one instanced unit box per opaque part, scaled to the part's bundle bounds. Scenes without tiers cast from the detailed geometry. Transparent parts don't cast.
- **OIT:** three's `OITPassNode` (McGuire and Bavoil).
- **Frame cadence:** three's pass and shadow nodes refresh once per animation frame, so measured frames each wait for one `requestAnimationFrame` before the timed submit-to-GPU-done interval.
- **2D plan view:** the editor's plan view renders through an orthographic camera and skips the post pipeline, so it has no outlines, bevel glints, GTAO or FXAA; the plastic material, IBL and shadows still apply. The edge pass assumes a perspective camera throughout (`perspectiveDepthToViewZ`, a view direction per pixel, edge fade by projected stud pitch at each depth), and three's pass and GTAO nodes bind one camera when they are built. Outlines in the plan need a second `LookPipeline` built for the orthographic camera, with orthographic view depth, a constant view direction and a stud pitch from the plan's scale, which is a separate change to the look pass. Under D6 the 2D plan backend (above) replaces this view as the plan in B2.7, so that change isn't scheduled.
- **Ground, grid and scale bar:** the editor draws one ground plane at the measured table plane (y = −t from the bundle's `tablePlane`), so baseplates cover it and the gaps between them show. It is a backdrop: drawn first, with no depth test or depth write, so models and the rooms and tables of plan regions, which sit below the table plane, always draw over it, and the post pass reads it as sky (no outlines or AO on it). Lines every 1, 8 and 32 studs are drawn in its shader, anti-aliased from screen-space derivatives, and each set fades out as its on-screen spacing drops below a few pixels, so the finer lines vanish with distance and zoom. The 8-stud step divides the 32-stud chunk, so the lines stay on world stud lines when the render origin rebases. In 3D the ground fades into the sky colour between 2.5 and 9 eye distances (capped below the far plane); the 2D plan has no fog. The grid reads no module, profile or world data. Placements don't snap to it; only the table tool's drawn table edges land on its 8-stud lines (§7.3), and table tops carry the same lines in the same shader. `#` hides and shows the lines, on the ground and on table tops. The 2D plan also shows a scale bar, a power of two studs long with its length in mm, cm or m at 8 mm per stud, at most 120 CSS px wide and true to the orthographic scale the renderer draws. Viewer scenes draw no ground.

**Picking.** GPU id picking at model granularity. Under D2 nothing below model level is ever picked, except switch levers and vehicles. *M1 S5 status:* the editor picks on the CPU: a ray against the ground plane (y = 0, the baseplate top) for placement, and against each placed model's world AABB for selection. A placed model's part and stud instances go into the render chunk that contains each instance, and only the chunks it touches are rebuilt.

**Path select.** Double-clicking a laid track piece in select mode selects its run, and Shift-double-click selects every piece joined to it. Both walk the track graph (`TrackPaths` in `domain`) over laid track and track carried by placed models alike. A run leaves each piece it enters through the routes of the end it came in on, so it goes straight through a crossing on one line, and it stops at open ends and before any piece one of whose ends has more than one route. That topology, read from the piece's own routes, is what makes a piece a switch; no part number or catalog kind is consulted. The clicked piece's own run leaves through all of its ends, so a switch's run is the switch and the plain track off each of its ends. Routes are marked walked one at a time, so a run that loops back through the same crossing on its other line carries on past it. Track carried by a model is selected as that model, the unit a user's own file moves as, so a run that reaches a switch through a model's own track takes in the model. A double-click anywhere else (a model, a train, empty ground, a held tool, or while a train runs) frames the selection as before. A double-click on a switch also throws it twice, since each click throws it, so it ends where it started.

**Budgets** for the 3D view (Tier A: Iris Xe, Apple M1 or Radeon 680M at 1080p and 60 fps; the 2D plan's are under *2D plan backend* above):
- GPU ≤ 12 ms and main-thread render CPU ≤ 4 ms.
- ≤ 5M visible triangles.
- ≤ 1 GB GPU memory.
- Placing a model shows up in ≤ 50 ms; rebuilding the far LOD takes ≤ 1 s and runs asynchronously.
- A 250k-part layout is interactive in ≤ 10 s cold and ≤ 3 s warm.

**Upgrade path.** `SceneBackend` takes chunked lists of model and part instances. If M0 or M6 fails the gates, a custom WebGPU backend can replace three.js underneath it without touching the data model. That backend would use compute culling, Hi-Z occlusion and vertex-pulling indirect draws (engine stack §4).

## 7. Validation (scoped by D2)

### 7.1 Model badges (computed at import, never blocking)
| Badge | Check | Needed for |
|---|---|---|
| L1 Real elements | Every (part, color) pair is in the element-existence table | "Real set", "Verified model" |
| L2 Matches set N | Normalized BOM diff against the Rebrickable inventory: *exact*, or *buildable from* the set (combined inventories for multi-set builds). Prints relaxed by default. | "Real set" |
| L3 Structure (unscheduled) | Connection graph from the LDCad and inferred connectors: no floating parts, no interpenetration outside connection zones | "Verified model" |
| Provenance | The model contains unofficial, custom or placeholder parts | Shown as a warning |

Failing a badge never blocks placement. Users fix their bricks in their own CAD tool and re-import. Stability analysis is out of scope.

### 7.2 Layout rules (live and exact; they decide whether a layout is "Valid")
1. **Real catalog items only.** `thirdParty` parts are refused unless `allowThirdParty` is on, which it isn't in this release.
2. **Lattice placement.** Models, plates and baseplates sit on the 20-LDU lattice with 90° rotations, at whole plate heights.
3. **Support.** A placed model's base footprint engages at least one stud of what lies beneath it, or rests fully on a flat area at one height.
4. **No overlap.** Placements' occupancy and keep-out volumes don't intersect, except at declared connectors.
5. **Track.** Ends join exactly (§5.3) and only at equal heights. Open ends are errors unless capped by a buffer part or marked open by the user. Track at an angle off the lattice can't claim stud support and must rest on flat support. A run may ramp between heights in whole plates per piece; the grade is unverified (see *Raised track* below).
6. **Clearance.** The profile's parallel spacing is respected, and the swept envelope of the widest and longest consist placed on a layout is checked along curves and switches. S-curves without a straight between them get a warning.
7. **Roads.** Road edges that meet have equal lane and curb patterns. Plan validation reports a mismatch; placement never refuses it (D3). Track over any road cell at its bed is a level crossing site, a tiled plaza's as much as a roadway's, judged on each road cell's own square, and level crossings must use real crossing parts. Track there that doesn't seat on studs is still reported unsupported.
8. **Modules** (when a profile is active): modules are on the 32-stud grid, edge connectors are present and aligned, and the surface height matches the profile.
9. **BOM flags.** Third-party parts, mixed 9V and plastic track in a powered loop, and any use of the optional "real-world play" tolerance mode (off by default and never counted as Valid).

**Track systems.** The track tool offers one drawing kit per track system in the catalog that has a straight and a curve (today 9V and 6-wide plastic), each its own palette tool named from its parts' titles and curve radius. Every catalog piece of every system can be held and laid on its own, and laid pieces of different systems join wherever their ends meet exactly, as the physical clips do. Play stands trains on the rail of the system most of the laid track belongs to.

**Raised track.** The track tool draws at a height in whole plates (Page Up and Page Down, Shift for a brick, or the *Track height* panel). The cursor follows that plane.
- **Runs.** A new run starts at the drawing height. A run from an open end starts at the end's height and ramps toward the drawing height on its straights first, then its curves, at the chosen rise per piece (1 or 2 plates), and runs level once there. A run that joins an open end must reach that end's height exactly, or it's refused as too steep. Ends join only at equal heights, so a ramp's high end joins only track at that height.
- **Ramp pieces** keep their exact ℤ[ζ₁₆] plan poses and are drawn sheared between their end heights; `TrackRecordV1.rise` stores the rise. A tilted straight is 0.1000 LDU shorter in plan at 1 plate and 0.4003 LDU at 2 (`verified-facts.md`, Elevation). **The grade is unverified:** 1 plate per 16 studs is one club's convention (S8), and no source gives a maximum for LEGO trains. A tilted piece rests at its ends, as a real ramp does: it counts as supported when each end either joins level track that is itself supported, or has an anti-stud of its end row (the row nearest that end) exactly on a stud whose top is at that end's height, such as a pier's, a ramp support's or a user's own brick's. Stud cells and heights compare exactly, with no tolerance. A ramp piece with an end resting on neither is reported unsupported. When a run is laid, every raised ramp end that doesn't join level track gets a generated pier at its height, exempt from collision with the pieces resting on it, unless something already holds it.
- **Support** is the one track-support rule: a piece at a raised band is held only by an anti-stud exactly on a stud of a model whose studs are at that band; air is never support, and there is no table above the ground band.
- **Piers.** After a run is laid, every raised level piece that nothing holds yet gets a pier: a generated LDraw file of real parts (`track-pier-<n>-plates.ldr`: 3001 bricks, then 3020 plates, in Light Bluish Gray), imported through the same import path as a user's file and placed through the solver like any model, so it seats on whatever studs are beneath and appears in the BOM. Course heights are measured from the parts' own connector records (top studs to bottom anti-studs). The pier's site is found from the piece's own anti-studs: each lattice pose where the pier's top studs meet them is ranked by how many meet, then by distance from the piece's centre, and the first that passes the model checks (collision with models and track, support) is used. The run and its piers are one undoable edit. A user's own pier or viaduct model holds track by the same rule, and no pier is generated for a piece it already holds. A piece with no free site (for example a bridge piece whose only sites stand on the track below) is laid and reported unsupported.
- **Over and under.** Placement stays physical: track at another height blocks a new piece only where their solid heights meet, and a train standing on the track below is a solid obstacle too (each vehicle's footprint from its rail top to its roof, studs included), so a bridge that would hit it is refused, naming the train. A train can't be seated where it would hit raised track other than the pieces it stands on. It can stand on raised track and ramps wherever it fits. Clearance is a layout rule, reported rather than refused: a crossing whose gap from the lower rails to the upper underside is less than the tallest train's height is laid, and the upper piece gets a `clearance` finding ("too low for the tallest train: 10014-1 needs 39 plates, this bridge has 38"), a plan issue inside a plan region and a warning in the HUD and track panel. The tallest-train height is computed at runtime by `ITallestTrain` (`trains/tallest-train.ts`) over `IPlaceableCatalog.rollingStock()`, every train-bearing placeable in the catalog, bundled or imported, and measured again when a train is imported: each vehicle's top (its body and bogie part bounds with their studs, `PlayModel.vehicleTops`) above its 74746 rail contact. The rail yard's footprints use the same vehicle tops, and both clearance and Play take the rail top from the kit straight's measured top. Until a train is measured, crossings aren't judged.
- **Height labels** show the plate height of every raised end and joint, the ghost run's end, and the clearance at every crossing ("36 plates (115.2 mm) clear").
- **Trains on ramps and raised track** stand and run at the drawn rails' height. Each laid piece's rail height (its plates up plus the ramp's vertical shear, the same shear the piece is drawn with) is part of the sim track. The running-gear poser writes a height and pitch for every body and bogie into the vehicle pose: a bogie pitches to sit on both its axles, and the body pitches between its pivots. The sim's model check, the seat check and the renderer all pose parts from that same pose (`writeRigidFrame`, the matrix the renderer builds), so a train is checked where it's drawn.
- **Known limits.** Vehicles pitch but don't roll, so on a curved ramp, whose rails tilt a little sideways, they ride level across the track. A pitched body is rotated about its own origin and keeps its plan pose from the flat poser, so its plan length isn't shortened by the pitch's cosine (about 0.1 % on a 2-plates-a-piece ramp). Raised curves off the stud lattice can't mate studs, so they report unsupported unless something holds them exactly. Switches and crossings are laid level. Piers stand at the ground band only.

Layouts can always be saved in an invalid state. They then show as **Draft** with a list of issues.

**How strictly rules apply depends on the mode (D4).**
- In the **sandbox** (outside plan regions), rules 1 to 9 show as warnings. Building never stops.
- Inside a **plan region**, the same rules are errors, and a region can only reach "Buildable as planned" (§7.3) with zero errors.

### 7.3 Plan regions and "Buildable as planned"
A plan region is a polygon in the world, aligned to the 32-stud grid, linked to a **physical footprint**:
- the room outline, doors and obstacles;
- tables: polygon, height and seams;
- access aisles;
- a maximum reach depth.

These are drawn in mm and snapped to the stud grid at 8 mm per stud. Room scans or imported floor plans come later.

In the editor, tables are drawn and resized on the canvas with the table tool (B), and every drawn edge lands on the 8-stud guide grid the ground draws. A table's size and position can also be typed in studs or cm. Both convert exactly to whole mm (8 mm per stud, 10 mm per cm), which is what the footprint stores. Drawing the first table starts a plan whose room just encloses it, from the chunk corner at or before its near corner. A table drawn or moved past the room grows the room to enclose it, moving the origin back by whole chunks when needed, so the region stays on the 32-stud grid and nothing already placed moves. A typed position outside the room is kept as typed and reported by the footprint rule. Table tops carry the ground's 1, 8 and 32-stud grid. Every plan edit is one step in the editor's undo history, beside placement edits, in the order they happened.

Whatever item is in hand (a baseplate, a road plate, a module or a user's imported model) can be filled across an area, by dragging a rectangle or by filling the active plan's tables. The user picks an 8-, 16- or 32-stud fill grid (Shift+G); changing it or turning the item mid-drag lays the drag again from where it was pressed, and Esc cancels the drag and keeps the item in hand. The fill claims its own presses in place mode, so box select, moving a selection and arrow nudges (all select mode) never start during one, and picking an item clears the selection. Each tile's pitch is the item's own footprint in the current rotation, rounded up to a multiple of that grid. A dragged fill starts on the grid line nearest the press; a table fill starts on each table's first grid line inside it and takes only whole tiles. Every tile goes through the click's own checks: it rests at the height a click there would give, and it is refused where a click would be refused (a base that would overlap another at the same height, road that would lie on placed road at the same top, or a train that would stand on the rails). Road edges that mismatch, between tiles or against road already laid, are reported by the plan, not refused. Refused tiles are skipped and reported, never forced. A fill is one edit: one undo removes every tile and one redo restores them, and the plan counts them like any placement. One fill places at most 1,024 tiles and refuses a larger area outright.

Extra plan rules:
1. **Fits the footprint.** Every placement in the region lies on a table top, and nothing overhangs a table edge beyond the profile's limit (0 by default).
2. **Reach.** Every point of the layout is within the maximum reach depth from an aisle or table edge you can access. The default depth is an owner decision (§12).
3. **Seams.** Table seams fall on module boundaries, with a warning for any track that crosses a seam off a module edge.
4. **Complete BOM.** Every part is mapped to Rebrickable and BrickLink ids. Nothing is a placeholder. Substructure, baseplates, track and road plates are all counted.
5. **Real elements.** Every placed model has badge L1. Models claiming to be sets have badge L2, either exact or "buildable from".
6. All layout rules from §7.2 pass with zero errors.

The plan lists §7.2's track rule as rows read from the same exact join graph the track tool uses. Each open end is an error, and so is each point where track ends meet without joining: one row per point, and those ends aren't also listed as open. Laid track and a model's own identified track count alike. An end belongs to its laid piece, or to the model that carries it, and a row counts in every region whose room one of its pieces or models overlaps. Track the plan can't certify gets a warning naming the model or the laid pieces, the part and the count. Parts whose catalog connector poses are still unverified (§11) are identified, joined and drawn on those poses, laid and imported alike, because each such pose is derived from the part's own file (for 53400, its `!HELP` rotation point and end-marker headings) and is never a guess: the warning says their joins are only as exact as those poses, and the track tool that draws them carries an "unverified" badge. Parts the model places where no exact track pose fits are warned about too; their ends aren't checked and nothing joins to them, so an identified end beside one is listed as open. A warning keeps the plan from reading "Buildable as planned", as an error does, because that track went unchecked. Each edit sends the plan one delta, and an edit that changes laid track, or the track that models carry, includes the whole set of these rows. A region's list changes only when its own rows do.

Reversing loops and wyes are listed from the same join graph's topology, for every track system alike: nothing branches on a system, a part or a piece kind. Each route of a piece and each join is a link between two track ends, and every link joins the rail on one side of an end (looking out of it) to the rail on the other side of the next end. So a cycle of an odd number of links is one a train can run round and come back along facing the other way, and on it each rail runs round into the other, which shorts two-rail powered track such as 9V or 12V. `ReversingSectionFinder` (`domain/track/reversing-sections.ts`, bound to `REVERSING_SECTION_FINDER` and handed to each `TrackDrawing` by `TrackWorld`) splits the graph into its biconnected blocks of links and keeps each block that can't be two-coloured, which is exactly each block holding such a cycle. The plan lists one warning per block, naming every laid piece and every model with a route in it, so a balloon loop's stem, or the line between the balloons at the two ends of a point-to-point run, isn't named. The row's position is an end on one of the block's odd cycles where a train passes from one route of a piece straight onto another, the lowest such end on the cycle the two-colouring finds; for a balloon loop that's its switch's entry. Laid track and a model's own identified track count alike, so a user's file that holds a whole balloon, or holds the switch while laid track closes the loop, is reported the same way. It's a warning, not an error: whether track is powered isn't in its geometry, and unpowered track runs a reversing loop as drawn. Like every listed issue it keeps the plan from reading "Buildable as planned" while it stands. The plan's 2D marker for it comes with the 2D overlays.

A laid track piece is checked against the tables by its plan outline from the bundle, placed at its exact ℤ[ζ₁₆] pose, not by its footprint box. It overhangs the tables when part of its outline lies outside every table grown by the plan's overhang limit, the same limit and growth as rule 1 for every other placement. It stands across a seam when its outline has area on both sides of the seam line within the seam's span, as the seam rule asks of a model's footing. One crossing is excused: when one of the piece's ends sits exactly on the seam and faces across it, that end's face line is the seam line, so what lies across the seam is the part of the outline beyond that end face, its joiner tabs, and the joint is where the tables part. Both tests are exact: vertex coordinates that are rational in ℤ[ζ₁₆] compare as exact doubles, others with certified float bounds, and the rest fall back to ℤ[ζ₁₆] in BigInt. A model's own track is judged the same way. The pieces #553 identifies at exact poses are left out of the model's footing, which comes from the bake's per-instance footing pairs, and out of the box its overhang is measured by, which is the union of its other parts' boxes; their outlines, placed at the model's lattice pose, go through the same two tests with the same joint excuse. So a track container whose end sits exactly on a seam is judged like the drawn joint, and a wall standing in the cell a joiner tab reaches into is still judged by its own footing. Track in a run frame has no exact absolute pose, so it stays with the model's other parts; the plan lists that among the checks not made yet.

**Plan outputs:**
- a BOM for the region and for each module, in two views: "whole sets vs loose parts" and "own vs buy" (using an imported Rebrickable collection or CSV);
- Wanted List XML for the shortfall;
- a printable plan: a dimensioned top view on the tables, module numbering, track piece positions, switch ids, and one sheet per module listing its pieces and models;
- the plan exported as an LDraw `.mpd`.

The printable sheets (Plan panel, "Print sheets") all come from one draw list. `PlanDrawing` turns the plan into named layers (room, tables, obstacles, roadway, models, track, ramps, dimensions, numbers) in paper millimetres at a scale of 1:N. Geometry stays in LDU relative to the plan's origin inside one similarity, so lattice placements keep their integer coordinates and a track piece's ℤ[ζ₁₆] outline is converted to floats once, at export. It draws the room, each table with its width and depth in studs and cm, obstacles, every placement inside the plan (a model by its footprint box, a laid track piece by its plan outline from the bundle), roadway cells from road surfaces, and suggested crossing ramps by their outlines (dashed: they aren't in the parts list). `SheetComposer` lays the draw list out in one of four ways:
- **One sheet at 1:1**, sized to the drawing. This is the `plan.svg` in a plan file.
- **An image** at 1 to 32 whole pixels per stud: the same one sheet, with the plan drawn at 1:(32/p) so that a stud is p pixels in a PNG at 4 px per mm (about 102 dpi), while the title block, legend and key keep their paper sizes and stay readable at any p. At 32 px per stud the plan is at 1:1. Its check bar is stated in pixels at 4 px per mm, which holds in every format.
- **Fit to one page** of A4, Letter or A3, at the largest ISO 5455 scale (1:1, 1:2, 1:5, 1:10, …) whose drawing fits beside the legend and under the title block.
- **Tiled** at 1:1 to 1:100 over pages of that paper, portrait, landscape, or whichever needs fewer pages. A cover comes first, with the title block, the legend, an index of the pages drawn over the plan at an ISO scale, and the key. Each page overlaps its neighbours by 5 to 30 mm. Registration marks sit on the seam lines inside the overlap, at the quarter points of every shared edge and at every four-page corner, so both pages print each mark whole at the same place on the plan. Each page carries only the items that reach its window, and its footer names the page by column letter and row number, its neighbours and the scale.

Every page has the trademark disclaimer, and every drawing page a check bar that measures 64 mm at 100% and stands for 8·N studs at 1:N. The title block gives the room, the number of tables, the scale, the verdict from `buildableAsPlanned` and the parts list totals. The legend lists only what the sheet draws. Placements are numbered in the plan's own order (models as placed, then track pieces by index), whatever they are, so a switch is numbered like any other track piece. The key lists each number with its label and its part count, counted by the same code the plan's parts list counts with, totals them, lists the checks not made yet, and continues on further pages when it doesn't fit. Text is set in Courier and Courier-Bold, whose 315 glyphs are all 600/1000 em wide in Adobe's Core 14 font metrics, so centred and right-aligned text and the key's columns are placed exactly without a metrics table. The SVG writer writes one SVG per page, with strokes and type in paper millimetres at every scale, and a stored ZIP of them when there are several. The PDF writer (`PDF_SHEET_WRITER`, no dependency) writes the same pages into one PDF 1.4 file: each page's media box is the paper at 72 points per inch, and its content stream draws in millimetres under one `cm`, so a 64 mm bar is 181.4173 pt. Text uses the standard Courier and Courier-Bold fonts in WinAnsiEncoding, so nothing is embedded; a character outside WinAnsi prints as "?", and the download lists those characters (the SVG keeps them). Streams are uncompressed, the file has no dates, and its `/ID` is a hash of its own bytes, so the same plan always writes the same bytes. The PNG writer (`PNG_SHEET_WRITER`) rasterises every page at 4 px per mm: it splits a page into equal tiles of at most 4096 px a side (BlueBrick's limit), named by column letter and row number, culls the draw list to each tile, gives each tile of a split page a 24 px footer below its part of the page that carries the trademark disclaimer, and has the browser draw that tile's SVG on a canvas and encode it, one tile at a time. One tile downloads as a `.png`, several as a stored ZIP of them. Its bytes come from the browser's rasteriser and PNG encoder, so unlike the PDF they aren't promised identical across browsers. Each plan's sheets are **named sheet sets** (`SHEET_SETS`): a name, which of the draw list's layers the sheet shows, whether it shows the plan with its key or the table plan, and the sheet's own layout and format. A plan starts with a "Main plan" (every placement layer, tiled at 1:1 on A4) and a "Table plan" (room, tables, obstacles, dimensions and table numbers, fitted to A3). Users add, rename, re-layer and delete sets, so a "Yard plan" is a set with only the layers the yard needs; "Download all sheets" writes every set into one PDF, or one ZIP of SVGs or PNGs, in order. A set's key lists only the placements its layers draw, under their plan-wide numbers, so sheets cross-reference. The table plan colours each table by its height from the Okabe–Ito palette (heights in rising order), numbers tables in the plan's order at their centres, and replaces the key with a schedule of each table's number, colour, height, size, lattice studs and distance from the left and back walls. Sheet sets live with the session, as plan regions do; they persist with the world once plans do (B1.2), and document layers (B1.3) will join the draw list's layers in the same sets. Switch ids and per-module part sheets come later.

## 8. Simulation

- **Where it runs.** A fixed timestep of 60 Hz in a worker. Simulation state is kept separate from render state, so it can run headless in tests.
- **Track graph.** Derived from track-end joins. Nodes are the joined ends, each with a pose. Edges are the part's `trackPaths` (straight or arc, with exact length). A switch is a node with one entry, two exits and a state. Each physical edge gives two directed edges, so reversing loops and wyes work.
- **Trains.** A consist is an ordered list of vehicles. Each vehicle has a length, bogie offsets, coupler points, max speed, acceleration and braking, a power system (9V, PF, PU or none; cosmetic) and discrete power steps.
  - A train's position is (directed edge, offset). Cars are placed by walking back along the path, and bogies pivot. A pivoting bogie's two axles are solved onto the centreline at their true spacing, symmetric about the bogie's place on the path, so on a curve neither stands off the rails (the arc between them is longer than their chord).
  - **Trains stand on the rails.** A held model with detected running gear seats on laid track under the cursor: its head (the leading coupling face) goes a whole number of LDU along one route of one track piece, centred on the cursor and slid back from open ends, and its bogies are posed with the same poser the sim uses, so Play's first frame is the placed pose. Off the rails it places as an ordinary model. Two trains never hold the same track piece, which is the sim's per-piece reservation. Play runs every train on the rails from where it stands and drives one chosen train at a time.
  - **The anchor is the piece's exact pose**, never its index: the catalog piece, its ℤ[ζ₁₆] pose in the world track frame and its height. Laid track and certified track inside placed models both have one. Track in a run frame (off the stud lattice inside its model) has none, so a train can't stand on it yet.
  - Control is manual throttle plus "go to": A* over the directed graph, throwing switches automatically.
  - The MVP prevents collisions by stopping a train on occupancy. Signals aren't planned (§13, *Not doing*).
- **Vehicle data.** A sidecar file attached to the model hash holds the kind, bogies, couplers, axles, length and suggested minimum radius. It can optionally round-trip as `0 !BRKRR VEHICLE ...` metas in the LDraw file.
  - Bogies must be separate submodels. When they aren't, the user re-exports from their CAD tool.
  - A metadata-only "designate parts as bogie" tool is unscheduled. It would group parts and edit none.
- **Roads (unscheduled; D6 freezes Play features).** Lanes are directed edges with turn connectors at intersections. Cars use IDM-lite car-following. Intersections start with first-come or stop-sign rules, with traffic lights later, plus ambient traffic.
- **Derailment at open ends (in scope now, manual Play mode only).**
  - **Rule.** A manually driven train under the opt-in `derail` open-end rule doesn't brake for an open end. It keeps running until the leading axle of its leading guide leaves the rail, taken from the imported running-gear geometry. Then it derails and skids to rest along the end's tangent. A train that stops with only its front overhanging stays on the rails. Rerail puts a derailed train back at the track end.
  - **What doesn't change.**
    - Routed and autopilot trains still stop where their route ends.
    - The default `brake` rule still stops every train short of an open end.
  - **The skid** at the train's braking rate is a game choice, not a physical model.
  - **Decision.** Made by the project coordinator under the owner's delegation of design decisions, to serve the owner's request for a product that is fun, playful and correct (2026-11-17).
- **Out of scope.** Physics beyond that rule, derailment anywhere else (curves, switches, collisions), grades and power draw, pedestrians, economy, signals and timetables.

*M1 S9 status:*
- **Schema.** `@brr/schema/world` defines world schema v1 as valibot `strictObject` schemas, each type inferred from its schema (`WorldManifestV1`, `WorldShardV1`, `PlacementRecordV1`, `WorldIndexEntry`, `TrackRecordV1`, …):
  - a manifest with `format`, `schemaVersion`, `name`, `bundleVersion`, the placement and track counts, the shard list, the saved camera `view`, `credits` and the trademark `disclaimer`;
  - one shard per 8 × 8-chunk super-chunk, holding the placements (`ref`, `color`, x, z, `yPlates`, `rot`) whose x and z fall in it, and the laid track pieces (global `index`, `ref`, heading 0–15, the eight exact ℤ[ζ₁₆] coefficients of the position, `yPlates`) whose position falls in it.
- **Canonical form.** Keys are sorted with no whitespace. Shards are sorted by super-chunk, placements by value, and track by index. The editor builds each chunk's instances in the same value order, so a reloaded world draws the same pixels. Everything read back goes through `decode` from `@brr/schema/decode`, which returns issue lists. The schemas check that poses sit on the 20-LDU lattice, that each placement lies inside its own super-chunk, that a newer schema version is refused, that no unknown keys appear, and that the counts agree.
- **IndexedDB.** `@brr/storage` gives each world its own database `brr-world-<id>`, with a `manifest` store and a `shards` store. Each value is the canonical JSON text, keyed by `sx_sz`. A `brr-worlds` database indexes the worlds. Each edit, including undo and redo, rewrites only the shards it touched, plus the manifest. A track edit rewrites the super-chunks that hold track and those that held the pieces it lifted, so an undone run leaves the save too. Placements loaded from a save are adopted into a fresh `EditHistory`, so opening a world starts with empty undo and redo stacks. Camera moves are saved after 0.5 s.
- **Export.** `*.brr.zip` is a stored (uncompressed) ZIP with fixed 1980-01-01 timestamps. It contains `manifest.json`, then `shards/<sx>_<sz>.json` in order, then `CREDITS.txt`. That file is the S10 credits text (`ICredits.exportText`), with the OMR set credits narrowed to the sets placed in the world. The LDraw file list stays bundle-wide, because the manifest doesn't record which subfiles each part draws on. The same world therefore always exports the same bytes.
- **Import.** Import reads stored or deflated entries, checks each CRC, refuses encrypted entries, and refuses any placement `ref` and `color` pair that isn't in the catalog, and any track `ref` that isn't a drawable piece, rather than substituting something.

*B1.1 world schema v2 status:*
- **Version.** The app writes world schema v2 and reads v1 and v2. `readWorldFiles`, `decodeWorldManifest` and `decodeWorldShard` read `schemaVersion` first and refuse a newer one with one message; a v1 manifest or shard is migrated as it's read, so v1 archives, starters and worlds an earlier version saved in IndexedDB keep opening. Migration only adds the v2 fields at their defaults: the base layer, no notes, and `schemaVersion` 2. Every v1 placement and track record is already a valid v2 record. `packages/test-fixtures/world-schema/` holds a hand-written v1 world, its expected v2 migration byte for byte, and a v2 world that uses every field. In IndexedDB a world keeps the v1 shards it hasn't rewritten beside the v2 ones, and each shard is read by its own version.
- **Document tables in the manifest.**
  - `layers`: the ordered layer table, drawn bottom to top, each with an integer `id` (0-65535), `name`, `kind` (`parts`, `notes` or `plan`), `visible`, `locked` and `opacity` (an integer percentage). Layer 0 is the base parts layer. It's always present and can be renamed, reordered, hidden or locked, but it can't be removed or change kind.
  - `groups`: groups as `{ id, name, parent? }`, listed in ascending id order. Parents must be listed and no group may nest inside itself.
  - `contributors`: the roster as `{ id, name, color }`, with colours as lowercase `#rrggbb`.
  - `plans`: the plan regions in the `.brrplan.zip` record shape, each on a `plan` layer, and `activePlan` as an index into them.
  - `event`: optional `title`, `author`, `club`, `event`, `venue`, `startDate`, `endDate` (calendar dates `YYYY-MM-DD`, and an end needs a start no later than it) and `comment`.
  - Empty tables are left out, as `consists` is.
- **Record tags.** Placement and track records may carry `layer`, `owner` (a contributor id) and `group` (the innermost group). A record without `layer` is on layer 0, and writing `layer: 0` is refused, so each record has one spelling. A record's layer must be a `parts` layer the manifest lists, and its owner and group must be listed. The archive reader and the repository check these references on read and save. Layers never change physics: hidden and locked parts layers still collide and still count.
- **Note shards.** Notes are never parts. They live in their own `notes/<sx>_<sz>.json` files (`format` `brr.notes`), listed in the manifest's `noteShards` with a `notes` total, so editing a note never rewrites a parts shard. Each note has a global `index` (dense from 0, which is its draw order), a `layer` (which must be a `notes` layer), an optional `owner`, and a `kind`:
  - `zone`: a named, coloured polygon of at least three corners on the stud lattice, enclosing area. It's written from its lowest corner, counter-clockwise.
  - `text`: text at a stud, a quarter turn and a height in studs.
  - `ruler`: two ends, each a free point in whole LDU or a point offset in whole LDU from a placed model, which is named by its record fields as consists name a model.
  - `legend`: a position, an optional title and colour rows.
  A note is filed in the super-chunk of its anchor: a zone's lowest x and lowest z, a text's or legend's position, or a ruler's first end (the model's position for a model end).
- **Event panel (B1.8).** The Event panel, in the right column before the Plan panel, edits the manifest's `event`. Text is trimmed, blank fields are left out, and clearing every field removes the record. The draft is checked by `EventRecordV2` as it's typed, and each issue shows under its field. Apply records one `event` step in the editor's single undo history. The world saves it, and undo and redo save what they restore. A world that is read-only in this tab can't be edited. The panel also gives the layout's size: the width and depth of the union of the plan boxes of every placed model, baseplate and track piece. These are the boxes Fit all frames, taken from baked geometry and the bundle's track outlines. The size is shown in studs, 96-stud modules, metres and feet, at 8 mm a stud and 304.8 mm a foot. Plan regions don't count towards it. If a box can't be read, the size is reported as unmeasured, never guessed.
- **Not in v2 yet:** floor-plan underlays (B4.3), which need image files in the archive and the store. The editor doesn't yet hold layers, groups or owners (B1.3, B1.5, B4.4), so it refuses to open a world whose records carry them rather than drop them on the next save. It does keep the manifest's document tables and note shards through saves, exports and imports. `.brrplan.zip` is unchanged: it still writes v1 shards, with no tags, and its shards are migrated to v2 when it's opened.

*B1.6 notes status:*
- **Service.** `IAnnotationService` (`ANNOTATION_SERVICE`, `packages/client/src/notes/`) holds the open world's notes as `NoteEntry` rows: a session id (`note-N`, never saved) and the v2 note record, whose `index` is always its position. `add`, `update` and `remove` take a note body (the record without `index`) and return issues instead of throwing. A body must decode as a v2 note, name a `notes` layer and a contributor the manifest lists, and every ruler end attached to a model must name a placement the world holds, by its whole record. Zones are stored with the outline `canonicalOutline` writes, so the state is what the shard holds. A read-only tab refuses every edit. The pure state functions (`followPlacements`, `modelEnd`, `rulerEndPoint`, `withNote`…) live in `packages/domain/src/notes/`.
- **History.** Each note edit is one `EditHistory` step of kind `note`, carrying the whole note state before and after, as plan edits carry plan state. Undo and redo restore those snapshots.
- **Rulers on models.** A model end stores its offset in the model's own frame (the same `rot90` convention placements draw with), so it marks the same spot on the model through every move and quarter turn. `EditHistory` asks its `PlacementFollower`, the annotation service, for the note change of every placement edit and records it in the same step, so one undo puts the model and its rulers back together. Every end that names a moved placement's old record names its new record; all of one edit's moves apply at once, so models trading places trade ends. An end whose model is removed becomes a free point where it last was, so a saved model end always names a placed model; a ruler whose freed end lands on its other end measures nothing and goes in the same step. A world whose ruler names a model it doesn't place is refused on open and import. Rulers attach to placed models only, as the schema says; laid track isn't a placement.
- **Saving.** `WorldSession` marks notes dirty on any edit that carries a note change and saves, beside that edit's parts shards, only the note shards whose canonical text changed since the last save that succeeded, and drops note shards left empty. Removing a note renumbers the notes after it, which rewrites their shards. Export writes the live notes.
- **Not yet:** drawing notes (B2.6) and the zone, text and ruler tools (B1.7). Layers are read from the manifest when the world opens; the layers service (B1.3) takes over that table. `?state=1` shows the notes, with each ruler's resolved ends, in `#note-state`.

*B1.2 plans persist status:*
- **Saved with the world.** Plan regions (room, tables, obstacles, overhang and reach limits) and the active plan are saved in the manifest's `plans` and `activePlan` with every save, export and import, so tables drawn in a world are still there after a reload. `.brrplan.zip` is unchanged.
- **Codec.** `packages/client/src/plan/plan-document.ts` is the one place that maps between `PlanService` state and the document. `planStateOf` gives a world's plans session ids that `PlanService` never mints (`saved-plan-<i>`, with `-table-<j>` and `-obstacle-<k>` inside it). `withPlanState` writes every plan on the layer the world's plans already use, else its first plan layer, else a new visible, unlocked "Tables" plan layer at the bottom of the draw order with the lowest free id. A world whose plans lie on more than one plan layer is refused when it's opened, because the editor can't hold layers until B1.3 and would move them onto one on the next save.
- **Opening and saving.** The session decodes the plans as it opens a world and the editor restores them into `PlanService` as it replaces the world, so opening a world without plans clears the previous world's, and opening isn't an undo step. The editor reports `PlanService`'s state to the session whenever its regions or active plan change (a plan edit, its undo or redo, an opened `.brrplan.zip`, or choosing another active plan). Unsaved plan edits count like unsaved placements: a failed save keeps them and refuses New, Open and Import until it's retried.
- **Read-only tabs.** A tab that holds a world read-only shows its plans but doesn't edit them: the table tool, the draw-tables command, plan undo and redo and the plan panel's editing controls are refused there. Choosing the active plan stays available as view state and isn't saved from that tab.
- **Empty worlds.** A world with plans and nothing placed isn't empty, so the welcome card doesn't offer starters over it.

*B4.1 table library status:*
- **Table types are world data.** A world's `tableTypes` (name, width, depth and height in whole mm, a colour and the count owned) are saved in its manifest with its plans and travel with `*.brr.zip`, so next year's event copies them with the world. There are no table presets in code (decision 13). `.brrplan.zip` stays v1 and carries neither types nor numbers; a plan file's tables open untyped and numbered in file order.
- **Numbers.** Every plan table has a number, unique within its plan. A new table, drawn, added or placed from the library, takes the lowest number its plan doesn't use, and numbers never change on their own, so a printed table plan stays right after a table is removed. A drawn or added table is named "Table <number>".
- **Placing.** A library table has its type's width and depth in one of its two orientations, and its type's height; the schema refuses a typed table that doesn't. The table tool places one with its back-left corner on the 8-stud grid; R turns it a quarter turn about that corner. A library table moves but doesn't resize. Editing a type resizes its placed tables about their back-left corner, keeping each one's orientation, in the same undo step. Removing a type leaves its tables as plain tables at their size. A direct edit that takes a library table off its type's size or height makes it a plain table, so a typed table always matches its type.
- **Placed against owned.** The library counts the active plan's tables of each type against the number owned and warns when a plan uses more than the club owns. That is a warning in the library, never a plan error, so it doesn't block "Buildable as planned": tables can be borrowed or hired, as missing parts can be bought (B4.6). Plan rules see library tables exactly as drawn tables: the table type changes nothing the checks measure.

*M5 plan export status:*
- **Format.** `*.brrplan.zip` (`@brr/schema/plan`) is the world archive's layout with a plan manifest: `manifest.json` (`format` `brr.plan`, `schemaVersion` 1, the bundle pin, the plan region without session ids, its overhang and reach limits included, the shard list and the output files), world shards holding exactly the rows plan sync counts inside the region (placements, and laid track renumbered from 0 in global order), `CREDITS.txt`, the printable plan `plan.svg` and the plan's parts list (`parts.csv`, `bricklink.xml`, `rebrickable.csv`), and `imports/<sha256>/<name>`. The printable plan and parts list are written for people and never read back; reopening rebuilds them from the plan. The archive is a stored ZIP like `*.brr.zip`; its manifest, shards, credits and model files depend only on the plan's contents (canonical JSON, entries sorted; laid track keeps its laying order, as worlds keep it), while the printable plan and parts list are the panels' own output for the session (the plan numbers placements in row order). Footprint millimetres are written as JSON numbers, exact for every finite value (−0 is written as 0, the same length). A different format or schema version is refused with one message before anything else is read.
- **What travels.** Every imported model the plan places travels as its original file under `imports/<sha256>/<name>`, as in `*.brr.zip`, whatever the licence headers of the parts inside it (owner decision, 2026-11-20). Compiled custom geometry is never written: the device that opens the plan compiles the file's own parts under the import's rules (§3.3). The credits list each imported model's authors and licences and every custom part it draws (file, title, author, licence).
- **Reopening.** Opening a plan file adds it to the open world as one undo step (`open-plan`): the region, made active, every placement at its saved pose and the track appended in saved order, all exact. The members are checked as one group at their saved poses, so they keep the support they had: saving refuses a plan with a model whose only mates are models outside it (counted with the outside models around the plan withdrawn from the placement search), or with no model standing on the table. It is refused when a ref isn't in the catalog or the paste checks refuse a member at its saved pose (a base overlapping a placed base, a model crossing laid track, a track piece blocked, road lying on placed road at the same top with road snapping on); then the world, its plans and the undo history are unchanged, and a model file the open read from the archive stays in the palette, as after a model import, without being stored.

*B5.1 BlueBrick reader status:*
- **What it reads.** `brick_compile::bluebrick` reads a `.bbm` (BlueBrick data versions 0 to 9; a newer version is refused with its number) into one document: the map properties (author, LUG, event, date, comment, background), then each layer in file order with its id, name, visibility, opacity and hull. Grid layers keep their lines and cell index; brick layers their bricks (part id as written, display area, orientation, altitude, active connection, group, connections) and groups; area layers their painted cells as RGB, since BlueBrick replaces each cell's alpha with the layer's; text layers their labels; ruler layers their linear and circular rulers and the bricks they're attached to. A layer type the reader doesn't know is skipped and reported, as BlueBrick skips it. `@brr/import`'s `BrickCompiler.readBlueBrick` runs it through the WASM compiler (`readBlueBrick` operation) and decodes the reply against `@brr/schema/bluebrick`.
- **Following BlueBrick.** Element names and version gates come from BlueBrick's own load code (`Map.cs`, `Layer*.cs`, `XmlReadWrite.cs`). Where a field is younger than the file, the reader uses BlueBrick's fixed default (opacity 100, altitude 0, no elevation labels) and reports `null` where BlueBrick falls back to the viewer's own settings (`showLines`) or the file has no such data (ids before version 6 or 7, hulls before 9). The event is read from `<Event>` or the `<Show>` it was called until BlueBrick commit `10d73ba` (2020), which kept data version 9.
- **Exactness.** Positions, sizes, orientations, altitudes, ruler points, radii and offsets keep the decimals the file printed, as canonical exact decimal text in studs or degrees; nothing is rounded to BlueBrick's `float`. Styling values (line and font sizes, dash patterns) are numbers. Ids are text, because BlueBrick's are 64-bit.
- **References.** Links, group membership and ruler attachments resolve to indices in the document, using one id table for the whole map as BlueBrick does. A link is kept only when both connections name each other; a missing target, a duplicated id, a link the other end doesn't return, a group that is its own ancestor (the closing parent is dropped) and an attachment to no brick are listed as `issues` and never guessed. The reader reads no BlueBrick part library, so it doesn't know where a part's connection points are; B5.2 and B5.3 map parts and re-lay track from LDraw geometry.

*B5.2 BlueBrick id mapping status:*
- **Reading an id.** `@brr/import`'s `BlueBrickPartMapper` maps each distinct brick id of a read map, and each brick-layer group id that names a set, the way BlueBrick splits them: at the last `.`, an integer suffix is an LDraw colour code; `<set number>.SET` is a set; an id starting `TABLE` is a table. Any other id (a set's pieces such as `4565-1.LOCO`, a drawing) is reported as `notAPart`. The result lists every id with its brick and group counts and its outcome.
- **Parts.** The number is read twice: as a file of the pinned LDraw library (`MirrorPartResolver`, through `LdrawMirror` and the compiler's `readModel`) and as a BrickLink number through the bundle crosswalk's `bricklinkParts`, because BlueBrick's library numbers some pieces by BrickLink number (`2889` is LDraw's puppy but BrickLink's monorail point). A `~Moved to` or `=` alias file is followed only when it only renumbers: one colour 16 reference at identity and no geometry of its own. A move that also turns or recolours its target (70 of the 1,662 in the pinned library) stays as the file itself. The part is taken when the readings agree or only one exists; when they disagree, or BrickLink names several parts, the id is `ambiguous` and both readings are listed. A `~` file that isn't a move is a component LDraw keeps out of part lists (`2859`, the 9V point's plastic body) and is reported as `component`. A colour that isn't an LDConfig code of the bundle is `unknownColor`.
- **Sets and tables.** `NNNN-N.SET` maps to the bundle's OMR model of exactly that name, or is `noModel`. `TABLE…` ids are tables: a `.bbm` gives a table's footprint (its display area) but not its height, which a plan table needs.
- **Nothing from BlueBrick's library.** No sprite, connection point, offset or `<LDraw>` remap is read; ids that neither LDraw nor the crosswalk knows (BlueBrick's half curves, third-party track) are reported as `notInLibrary`. B5.3 places the mapped parts.

*B5.4 BlueBrick notes status:*
- **Layers.** `@brr/import`'s `blueBrickNotes` turns a read map's layers into world v2 layer records in file order, with BlueBrick's name, visibility and opacity, unlocked. Brick layers become parts layers, the first one the base layer (id 0); a map without one keeps the default base layer. Area, text and ruler layers become notes layers. `layerIds` gives each BlueBrick layer's id, so the import that places bricks can put them on their layer. Grid layers aren't kept, since the plan's display grids replace them, and are reported. A blank name becomes `Layer N` (BlueBrick's own default, N the layer's position); so does a name too long for a label, which is reported.
- **Zones.** BlueBrick's area cell `(i, j)` covers studs `[i·s, (i+1)·s] × [j·s, (j+1)·s]` for cell size `s` (`LayerArea.getTotalAreaInStud`). Each 4-connected run of same-coloured cells is traced into one zone outline on the stud grid, named after its layer. A zone has no holes, so a run that encloses one, touches itself at a corner, or would need more than 4,096 corners is cut along a cell column (the hole's left edge, that corner, or the middle) until every piece is one simple outline. The pieces cover exactly the painted cells.
- **Labels.** A text becomes a label at the centre of its display area, rounded to the nearest whole stud, and turned to the nearest quarter turn (an exact half turns clockwise). BlueBrick turns clockwise on screen, and the plan draws north up with +z down, so BlueBrick's y is the world's z. The label's height is BlueBrick's em: the font size in points × 96/72, since BlueBrick measures text in pixels of a 96-dpi bitmap and draws one pixel per stud (`LayerTextCell.updateBitmap`). Alignment and font family aren't kept.
- **Rulers.** A linear ruler becomes a ruler between its two points, each rounded to the nearest LDU. Its ends stay points; an end attached to a brick is reported with that brick, for the import that places bricks to attach. A circular ruler has no equivalent and is reported. Offsets, units and styling aren't kept.
- **Colours.** An ARGB colour keeps its RGB. A named colour is a .NET web colour, because .NET saves any colour equal to one by name: `dotnet-web-colors.json` holds the 142 names and values of .NET's `KnownColorTable.cs` (dotnet/runtime `a0ec765`, MIT), which agree with the CSS named colours on all 141 they share. Any other name, such as a theme-dependent system colour, is reported and its note skipped, never guessed.
- **Event.** Author, LUG, event, date and comment become the event's author, club, event, start date and comment. A blank field is left out; a field the event can't hold (too long, not a calendar date) is reported.
- **Reported, never silent.** Every label centre or ruler end that rounding moved is reported with its displacement in LDU, every label that wasn't on a quarter turn with its angle, text and ruler groups (notes have none) per layer, and every note the world schema refuses (an empty label, a ruler whose ends round together) with the schema's reason. There's no caller yet: B5.5 builds the world from B5.3's placements and these records.

*B5.5 import as layout status:*
- **Split.** *Import as layout* takes an LDraw `.ldr` or `.mpd`, the shape BlueBrick's and Studio's LDraw exports take (BlueBrick writes one submodel per layer). The import worker reads it with the compiler, so a section is a submodel exactly when the compiler walks it as one. Each main-model line that references a submodel becomes its own file: the main model's meta lines, that line verbatim and only the sections it reaches. The main model's other lines become one more file, named after the original. A file without submodels stays whole. A Studio `.io` is refused with a pointer to Studio's LDraw export.
- **Placement.** Each file is imported like any user model, so it is stored by content hash, baked, credited and reopened as today. Every file keeps the layout's frame, so they're placed unturned, each at the first one's frame shift minus its own, which puts every part exactly where the file puts it, and the lowest rests on the table. A file whose rest plane isn't a whole number of plates from the first one's, within §5.3's 0.0005 LDU identification residual, can't sit at whole plates beside it, so it is left out and named, as is a file its own import refuses (a layer that draws nothing, say). The rest are held together like a paste and checked as one group where they're dropped.

## 12. Owner decisions still open (recommended default first)

1. **Definition of "real."** Default: official LDraw parts, in colors produced in at least one real element. Imports that fail get badges, not blocks; "Real set" and "Verified" need badges to pass.
2. **Layout validity.** Default: exact, zero-tolerance rules decide "Valid". Draft layouts can always be saved. A "real-world play" tolerance mode is off and never counts as Valid.
3. **Scale target.** Default: 250k parts loaded near the camera at 60 fps on an integrated GPU (MVP), 1M as a stretch. Total sandbox world size is unlimited, handled by streaming. Phones and tablets are view-only after the MVP.
   *Decided 2026-11-27 (D6):* the scale target is the show-scale reference world and its gates (§13). The 250k and 1M 3D figures stay as measured, with no new work. Total world size stays unlimited. **Tablets view and lightly edit:** the show-day view (B6.8) opens read-only, and a user with editor rights can unlock it to move, turn or remove placements and to add notes and comments by touch. Drawing track and roads, filling and importing stay desktop tools. Phones are view-only.
4. **Renderer path.** Default: three.js `WebGPURenderer` with WebGL2 fallback, behind `SceneBackend`. A custom WebGPU backend only if the M0 or M6 gates fail.
5. **Unofficial and custom parts in imports.** Default: allowed and rendered from inline geometry, with a badge. They exclude a model from "Real set" and "Verified".
   *Decided 2026-11-18 (owner):* custom parts in an import are compiled and drawn locally when every file they reach carries a CA `!LICENSE` header, with a `custom` badge, connectors inferred at import and flagged unverified, and a not-buyable BOM line (§3.3 step 2). Parts without that header stay reported and undrawn. A CA-licensed `Unofficial_*` part from the user's own file counts as custom and is drawn; the unofficial allowlist governs only parts from the library, the pipeline and the bundle. Import-time inference runs the library precompute's extractor over the part's closure: the pinned LDCad shadow files and verified project patches (tier 1), then LDraw primitives (tier 2), then geometry (tier 4). Each face keeps its source tier, and every face of a custom part is flagged unverified.
   *Updated 2026-11-20 (owner):* no licence gating. Every custom part is drawn whatever `!LICENSE` its files carry, or none; only one that can't compile, such as files that refer to each other in a loop, is refused and reported.

   *Updated 2026-11-27 (D6):* Play becomes a test run of the plan and gets no new features. Signals, stations and timetables are unscheduled (§13).
8. **Audience and accounts.** Default: adult fans and LUG planners on desktop. No accounts in the MVP, which avoids COPPA and moderation; P1 accounts are 13+ with a DMCA process.
   *Decided 2026-11-27 (D6):* the primary user is the layout coordinator planning a show. Next come club members, who contribute modules, models, trains and inventory and check and print their part of the plan; then solo builders planning a home layout; then organisers and visitors on read-only links. Desktop comes first, with tablets as item 3 says. **Accounts arrive in B6:** sign-in by email link, 13+, with a DMCA process (§10), because worlds and members' original files are stored in R2. Without an account everything keeps working locally, as today. The service stays free, with no ads.

   *Updated 2026-11-27 (D6):* prices are out of scope (§13, *Not doing*). Parts lists stay buyable through the BrickLink Wanted List and Rebrickable exports.

   *Updated 2026-11-27 (D6):* B3.6 adds a reversing-loop check for all track, read from track-graph topology (§7.3). It never branches on a track system. It is a warning rather than an error, because whether track is powered isn't in its geometry, and like every listed issue it keeps the plan from reading "Buildable as planned" while it stands.

### B1. One document
The document model. *Physical rules* are placement, joins, collision, support and the plan rules (§7).

| Concept | Meaning | Physical rules see it? |
|---|---|---|
| **Layer** | Named and ordered; visible, locked, opacity. Kinds: *parts* (placements and track), *notes* (zones, text, rulers, legend, underlay) and *plan* (room, tables, obstacles, aisles) | Parts layers: yes, all of them, shown or hidden. Real bricks collide whatever layer they're on. |
| **Group** | A nested, named set of placements that select and move as one | Yes, through the solver, like a multi-selection |
| **Kit** | A saved group (placements and track at exact relative poses) in a personal or club library | Its placed members are ordinary placements |
| **Zone** | A named, coloured area on the stud grid, optionally owned | No: never in the parts list, never joins, never blocks a part. Zone-on-zone overlap is an advisory issue. |
| **Text, ruler, legend** | Notes; a ruler can attach to placements and follow them | No |
| **Underlay** | A floor-plan image scaled by two points, with opacity and lock | No |
| **Contributor** | A roster entry (name, colour) set on placements, track, zones and inventories | No, except that it splits parts lists and budgets |
| **Event** | Title, author, club, event, dates, comment, title block | No |
| **Plan region** | The room, tables, obstacles, reach and seams of §7.3, saved with the world from B1.2 | Yes, as today |

The parts list can include or exclude hidden layers, as BlueBrick's does.

- **B1.1 World schema v2** (`@brr/schema/world`): plan regions in the manifest, a layer table, `layer` and `owner` on placement and track records, groups, note shards and event metadata. v1 files decode and migrate (a golden test), and v2 writes canonically.
- **B1.2 Plans persist.** `WorldSession` saves and loads `PlanService` state; `.brrplan.zip` is unchanged. Evidence: tables drawn, the page reloaded, the tables still there.
- **B1.3 `LayerService`** (`LAYER_SERVICE`): create, rename, reorder, show, hide, lock and set opacity. Locked layers refuse selection and edits, hidden layers aren't picked, and each change is an `EditHistory` step.
- **B1.4 Layers panel** and "Move to layer", and the parts list's "include hidden layers" option.
- **B1.5 Groups:** Ctrl+G and Ctrl+Shift+G (not Ctrl+U, which opens page source in Chrome), nesting, and a click selects the outermost group.
- **B1.6 `AnnotationService`** and the note types: zones (rectangles and polygons on whole studs), text labels, saved rulers attachable to placements, and the legend.
- **B1.7 Note tools:** zone, text and ruler tools in 2D and 3D, with keys assigned in the shortcut map.
- **B1.8 Event panel:** title, author, club, event, dates and comment, and the layout's size in studs, 96-stud modules, metres and feet.

### B3. BlueBrick-grade editing
- **B3.1 Click-to-append:** with an open end active, clicking a track piece in the library lays it exactly. The active end moves to the exit whose heading continues the entry's (for a switch, its straight exit), read from the piece's connectors. The piece just laid stays previewed on the new end, so Enter repeats it with the same hand. Space stays free for Space+drag panning.
- **B3.2 Blueprints:** an oval of N straights a side, a passing siding, a crossover and a yard ladder of k tracks, each solved by the exact closure solver from the active kit's pieces and offered only where it fits and crosses nothing. Two PRs: the solver entry points, then the palette section.
- **B3.3 Path select:** double-clicking a track piece selects its run to the next switch or open end, and Shift+double-click selects the connected network. Double-clicking a model still frames it.
- **B3.4 Find and replace:** swap item A for item B wherever B's connectors compose exactly at that instance, and list the instances it couldn't swap.
- **B3.5 Kits:** "Save selection as kit" to a personal or club library. A kit places as a group whose members connect by their own connectors.
- **B3.6 Reversing-loop check** (§7.3) from track-graph topology, as an issue and a 2D marker. It reports every loop or wye that reverses direction and says this shorts two-rail powered track such as 9V and 12V. It never branches on a track system. It is a warning, not an error, because whether track is powered isn't in its geometry; like every listed issue, it keeps the plan from reading "Buildable as planned" while it stands.
- **B3.7 Library search:** quoted phrases, `-exclude`, `#number` and colour names; Recent and Favourites; per-section filter memory.
- **B3.8 Loop closer:** when two open ends can be joined exactly, a one-click "close" that shows the pieces it would use.

### B4. Show planning
- **B4.1 Table library:** table types (name, width and depth in mm, height, colour, count owned), placed at 90° on the 8-stud grid, numbered automatically, with placed and owned counts. Table types are user data in the club's library; no table preset lives in code, and event templates are data files like starter worlds.
- **B4.2 Venue:** room rectangles, obstacles (pillars, doors and power points as markers), and aisles that mark the public and crew sides; the reach rule measures from aisles.
- **B4.3 Underlay:** a PNG or JPEG floor plan scaled by two points and a typed distance, with opacity and lock, stored with the world by content hash.
- **B4.4 Contributors:** a roster, assigning the selection, colouring by contributor, and an optional layer per contributor.
- **B4.5 Inventories:** per contributor, a Rebrickable collection CSV (extending today's own vs buy), a BlueBrick `.bbb` (through B5.2's mapping) or quick counts. The event budget is their sum.
- **B4.6 Budget on the library:** tiles show used and available. Over budget is a warning that feeds the shortfall Wanted List and never blocks "Buildable as planned", since missing parts can be bought. The parts list gains per-contributor and missing columns.
- **B4.7 Member sheets:** "what you bring" lists and per-contributor Wanted Lists.
- **B4.8 Show sheets** (§7.3, *Plan outputs*): one draw list, `PlanDrawing`, laid out by `SheetComposer` as one 1:1 sheet, fitted to one page, or tiled at true scale over A4, Letter or A3 with overlap and registration marks; a title block and legend; the table plan sheet (numbers, sizes, heights, colours); and named sheet sets as layer sets ("Main plan", "Table plan", or a user's "Yard plan"). It writes SVG, and PDF through a small vector PDF writer in `client` (`PDF_SHEET_WRITER`) with no dependency, fed by the same draw list, so its bytes are deterministic. Sheet sets persist with the world from B1.2, and document layers join the draw list's layers from B1.3.
- **B4.9 PNG export** at a chosen number of pixels per stud, tiled.
- **B4.10 LDraw `.mpd` export:** one submodel per layer, each placement a type-1 line at its exact pose, imported models embedded as their original files. Evidence: a round trip into LDCad or Studio.

### B5. Migration and interchange
BlueBrick XML is parsed in Rust (`quick-xml` in `brick-compile`), because workers have no `DOMParser` and `import` takes no XML dependency. Committed fixtures are synthetic `.bbm` files we write. BlueBrick's own tutorial layouts carry no stated licence, so they serve as local evidence only and are never committed.
- **B5.1 `.bbm` reader** in `brick-compile`, validated by `@brr/schema/bluebrick`: map properties, the grid, brick, area, text and ruler layers, bricks (part id, display area, orientation, altitude, links) and groups.
- **B5.2 Mapping** (§9, *B5.2 BlueBrick id mapping status*): each id is split as BlueBrick splits it, at its last `.`, into a part number and an LDraw colour code, a `NNNN-N.SET` set or a `TABLE…` table. A part number is read both as a file of the pinned library, following a moved or alias file only when it just renumbers, and as a BrickLink number through the bundle's crosswalk; it's taken when the readings agree or only one exists, and reported as ambiguous otherwise. A set maps to the bundle's OMR model of exactly that name. A table's display area gives its footprint, but the file has no table height. Everything else is skipped and reported; its outline can be kept on a "BlueBrick reference" notes layer.
- **B5.3 Track re-lay**, one connected component at a time. A `.bbm` holds float positions and hand-typed connection points, so its poses can't be identified to exact poses under §5.3. The importer pairs linked ends by geometry at the file's approximate poses (identification only; ambiguous pairs are reported), composes exact poses along the links from our own connectors, puts each component at the ℤ[ζ₁₆] pose nearest its anchor, and reports each component's displacement. No BlueBrick sprite or offset data is used. This moves a foreign file's track once, with every move reported; it is not a join tolerance, and joins afterwards compare exactly.
- **B5.4 Notes:** area-layer cells become zones merged into polygons on the stud grid, texts become labels, rulers become rulers, map properties become event metadata, and brick layers become parts layers.
- **B5.5 Import as layout:** an LDraw file's top-level submodels become separate immutable placements, for BlueBrick's and Studio's layout exports.
- Evidence: BlueBrick's tutorial layouts reopened locally, with their import reports and side-by-side images, and a synthetic `.bbm` built from official parts as the committed custom input.

### B6. Cloud and collaboration
- **B6.1 `apps/layout-api`:** a Cloudflare Worker with email-link accounts in D1, worlds as content-addressed shards and members' original model files in R2, and Terraform in `infra/cloudflare`. Compiled custom geometry is never uploaded; each device compiles a user's file itself, as today. It has the same allowed edges as `apps/catalog-api` (`schema` and `valibot`), and its PR adds it to §14.1, §14.2 and the dependency-cruiser config.
- **B6.2 `CloudWorldRepository`** in `storage`, behind `IWorldRepository`. IndexedDB stays the working copy, sync runs in the background, and a conflicting save becomes a new version.
- **B6.3 Share links** with viewer, commenter and editor roles, and a 2D-only read-only route.
- **B6.4 Comments** pinned to a point or a placement, threaded and resolvable.
- **B6.5 Live co-editing:** one Durable Object per layout orders `EditHistory` steps, and every client replays them. Deterministic open and canonical join order make the replay identical in every browser, and a cross-browser replay test proves it. Presence cursors show who is where, and a step refused after reordering is undone locally with a notice.
- **B6.6 Layer permissions:** contributors edit their own layers, and the coordinator edits all of them.
- **B6.7 Versions:** named snapshots ("BW 2027 v3") and a 2D diff overlay of added, removed and moved items.
- **B6.8 Show-day app:** an offline cache of a layout's glyphs and data, touch navigation, and read-only by default on tablets, with the light edits of §12 item 3.

### B7. Library scale

## 14. Code architecture

### 14.1 Repository layout
This is a **Turborepo** monorepo using pnpm workspaces, plus a Cargo workspace for the Rust compiler. The web app is built with **Vite**. Tests run under Vitest; end-to-end smoke tests (Playwright) start in M3. Package scope is `@brr/*`.

```
apps/
  web/                    Vite + React app; main-thread composition root
  catalog-api/            Cloudflare Worker: catalog search, set inventory and theme browse over D1; release files from R2 (D5)
packages/
  math/                   exact ℤ[ζ_N] arithmetic, lattice poses, Rot90, SoA vector helpers
  schema/                 valibot schemas for every wire and file format, one subpath each (bundle, catalog-api, world, decode); types are inferred from them
  domain/                 world/chunk store, placements, joins, track and road graph derivation, layout and plan rules, BOM engine, profiles
  sim/                    fixed-timestep simulation core (consists, routing, occupancy, later IDM-lite)
  catalog/                asset-bundle client: manifest, part records, connector tables, element-existence table, GLB loading
  import/                 import pipeline orchestration around compile-wasm: resolve, badges, bake
  compile-wasm/           generated wasm-bindgen output of crates/brick-compile (build artifact, not hand-written)
  render/                 SceneBackend interface, three.js backend, GPU buffer pools, look/post passes, plan overlay
  storage/                IndexedDB repositories (world shards, model blobs, collections, settings) and the asset cache
  rpc/                    typed worker message protocol, transferable typed-array envelopes, proxy helpers
  client/                 application services (OOP, Inversify): commands/undo, selection, tools, plan, BOM export, sim/import proxies; no React
  workers/
    import-worker/        worker entry + its own container
    sim-worker/           worker entry + its own container
    render-worker/        (only if a measured budget needs it) OffscreenCanvas entry + its own container
  ui/                     React components, hooks, design tokens; talks only to client service interfaces
  test-fixtures/          LDraw/.io samples, golden worlds and plans, benchmark scenes
  config/                 shared tsconfig and vitest presets (lint and format: oxlint and oxfmt at the root)
crates/
  brick-compile/          Rust: LDraw parse/flatten, BFC, normals, stud extraction, LODs, bake (lib)
  brick-compile-cli/      offline pipeline entry
  brick-compile-wasm/     wasm-bindgen wrapper → packages/compile-wasm
tools/
  asset-pipeline/         Node CLI: fetch/pin inputs, attribution, Rebrickable → SQLite → shards, connector merge, OMR ingest, publish
infra/
  cloudflare/             Terraform for the catalog Worker, its D1 database and its R2 release bucket (D5)
```

### 14.2 Dependency direction
Dependencies only point downward; nothing imports a package from its own layer or a layer above.

```
L6  apps/web                             apps/catalog-api (server; imports only schema)
L5  ui                                   workers/*  (entry points)
L4  client
L3  sim · import
L2  domain · catalog · render · storage · rpc
L1  schema
L0  math
```

| Package | May depend on |
|---|---|
| `math` | nothing |
| `schema` | math, valibot |
| `domain` | math, schema |
| `catalog` | math, schema, valibot, inversify |
| `render` | math, schema, catalog (asset formats), inversify — **not** domain; client adapts domain data into render buffers |
| `storage` | schema, inversify |
| `rpc` | schema, inversify |
| `sim` | math, schema, domain (graph types) |
| `import` | math, schema, domain, catalog, compile-wasm |
| `client` | math, schema (`@brr/schema/decode`, bundle wire types and running-gear overrides, world files), domain, catalog, render, storage, rpc, plus *types only* from sim and import (it reaches them through worker proxies) |
| `workers/*` | rpc plus their engine (`sim`, `import`, later `render`) and its dependencies, plus inversify. `workers/import-worker` also depends on `storage`, whose IndexedDB asset cache (`brr-assets`) holds the precompiled library-bake and connector records it reads; persistence runs in the main thread and the worker (§4). |
| `ui` | client (service interfaces, tokens, view models), schema types |
| `apps/web` | ui, client, workers (as `new Worker(new URL(...))` entries), and *types only* from schema (owner ruling, 2026-11-17: no re-export layers, so `apps/web` names wire types where they are defined) |
| `tools/asset-pipeline` | math, schema, domain, catalog, valibot, the brick-compile CLI; never imported by apps |
| `tools/e2e` | math, schema, catalog, import, client, render, storage and inversify; valibot, Playwright and Vitest. A test-tooling composition root like `apps/web` (owner ruling, 2026-11-19): it builds a `Container` from `client`'s `mainThreadModules` and rebinds only boundary tokens. Nothing imports it. |
| `apps/catalog-api` | schema and valibot only; `@brr/config` presets as dev tooling. Nothing imports it. |

**Enforced rules:**
- Every wire and file format is one valibot schema in `schema`, with its type inferred from it (owner decision, 2026-11-16). That covers the CDN bundle (manifest, model files, GLB JSON) and the palette that feeds its compiler, the catalog API and the D1 release rows behind it, and saved worlds. A query's projection of D1 rows is composed from the row schemas next to its SQL in `apps/catalog-api`. Packages that run schemas depend on `valibot`; packages that only name the types use `import type` from `schema`.
- `math`, `schema`, `domain` and `sim` are **pure**: no DOM, no three.js, no IndexedDB, no workers and no Inversify. They run unchanged in Node tests, in workers and in the pipeline.
- Only `client`, `workers/*`, `apps/web` and the L2 adapter packages `storage`, `render`, `catalog` and `rpc` import `inversify` (owner decision, 2026-11-16). Only `apps/web` and each worker entry **create containers**; they are the composition roots. `tools/e2e` is the one test-tooling composition root (owner ruling, 2026-11-19): it imports `inversify` and builds a container from `mainThreadModules`, rebinding only boundary tokens.
- `ui` never imports `domain`, `render` or `storage` directly. It goes through `client`.
- CI checks the boundaries with dependency-cruiser (§11 item 29, closed): one allow-list rule per package covering packages and third-party modules, global rules restricting `inversify` to the DI packages and `three` to `render`, and a rule failing any unresolvable import. `tsc --build` project references that mirror the table are still to come.
- Turbo tasks: `build`, `typecheck`, `lint`, `test`, `bench`, `wasm` (cached and keyed on `crates/**`). `apps/web#build` depends on `^build` and `compile-wasm#wasm`.

### 14.3 Services and dependency injection
- Application logic lives in **OOP service classes behind interfaces** (`ILayoutService`, `IPlanService`, `IBomService`, `ISimClient`, `IImportClient`, `ISceneBackend`, `IWorldRepository`, …). Pure engines from `domain` and `sim` are plain classes with constructor parameters, wrapped by services.
- **Every binding uses an explicit, typed symbol token.** Each package exports a `tokens.ts`:

```ts
import type { ServiceIdentifier } from "inversify";
export const LAYOUT_SERVICE: ServiceIdentifier<ILayoutService> = Symbol.for("brr.client.LayoutService");
export const WORLD_REPOSITORY: ServiceIdentifier<IWorldRepository> = Symbol.for("brr.storage.WorldRepository");
```

```ts
@injectable()
export class LayoutService implements ILayoutService {
  constructor(
    @inject(WORLD_REPOSITORY) private readonly repo: IWorldRepository,
    @inject(RULE_ENGINE) private readonly rules: RuleEngine,
  ) {}
}
```

- tsconfig sets `experimentalDecorators: true` and **`emitDecoratorMetadata: false`**. Vite's esbuild can't emit decorator metadata anyway, so nothing may depend on type reflection. A lint rule rejects `@inject()` without a token and rejects class-as-identifier bindings. Classes from pure packages are bound with `toDynamicValue(ctx => new RuleEngine(ctx.get(PROFILE_REGISTRY)))`, which needs no decorators. This is also the fallback for every binding if §11 item 28 finds problems.
- Bindings are grouped into one `ContainerModule` per package (`clientModule`, `storageModule`, `renderModule`, …). The two exceptions are `storage`'s `assetCacheModule`, the asset cache alone, which the import worker loads instead of `storageModule`, and `catalog`'s `linkProgressModule`, `LinkProgress` alone, which it loads instead of `catalogModule`. Composition roots load the modules they need, and tests load modules with fakes substituted.
- Services are singletons by default and are resolved once at startup or when a tool activates. **Nothing is resolved from a container in a hot path.**

### 14.4 Per-worker containers
- Each thread owns **its own Inversify container**, built in its worker entry from that worker's modules. No singletons and no service instances are shared across threads.
  - **Main thread:** client, render (MVP), storage and ui-facing modules. Remote engines are bound to **proxy implementations** from `rpc`: `SIM_CLIENT → SimWorkerProxy`, `IMPORT_CLIENT → ImportWorkerProxy`.
  - **Sim worker:** `sim` engine, a track/road graph snapshot and a clock. It exposes `ISimEngine` over `rpc`.
  - **Import worker:** `import`, `catalog` (read-only), compile-wasm, `storage`'s `assetCacheModule` (only the asset cache, shared with the main thread through IndexedDB; `storageModule` binds the same plus the main thread's repositories) and `catalog`'s `linkProgressModule` (only `LinkProgress`, which shares download progress with the other threads; `catalogModule` binds the same plus the main thread's catalog services). It exposes `IImportEngine`.
  - **Render worker (only if a measured budget needs it):** `render`, `catalog` and the OffscreenCanvas. The main thread then binds `SCENE_BACKEND → RenderWorkerProxy`.
- Cross-thread traffic only goes through `rpc` messages:
  - typed request and response unions;
  - versioned;
  - bulk data sent as **transferable typed arrays**, with SharedArrayBuffer rings reserved for when COOP/COEP is adopted.
- The same service interface has a local and a remote implementation, so moving an engine between threads only changes bindings.

### 14.5 Hot-path data rule
**Per-part, per-stud, per-instance and per-vehicle-car data never becomes a JS object.** It lives in typed arrays or GPU buffers, and code refers to it by integer handles.

| Data | Representation |
|---|---|
| Chunk placements | struct-of-arrays per chunk: `Int32Array` x/z, `Int16Array` yPlates, `Uint8Array` rot, `Uint32Array` refId, `Uint8Array` flags, a free-list for slots |
| Model instance lists (bake output) | `Uint32Array` partId, `Uint16Array` colorId, `Float32Array` 12-float matrices |
| Stud visibility | `Uint32Array` bitsets per model and per chunk |
| Occupancy | `Uint16Array` or `Uint8Array` column grids per chunk |
| Render instances | GPU buffers written straight from those arrays through pooled pages; CPU mirrors are typed arrays only |
| Sim state | `Float64Array` edge offsets and speeds, `Int32Array` edge ids per car, consist index ranges |
| Track graph | CSR adjacency in `Int32Array`s; exact `bigint` poses kept only on the edit-time join and validation path, never per frame |
| Element-existence table | a sorted `Uint32Array` of packed (part, color) keys, searched with binary search |

**Rules:**
- Zero allocations per frame and per sim tick. That means no closures, no iterators and no `Map`s keyed by part on those paths.
- The domain API hands out **views** (`ChunkView`, `PlacementHandle`) over the arrays. Objects are fine for cold data: catalog metadata, profiles, plan footprints, UI view models, and a single facade for the current selection.
- Exact `bigint` arithmetic runs only when editing or validating. The sim and the renderer use float64 or float32 data derived from exact poses.
- Enforced by review checklists and `bench` tasks: a frame and tick allocation probe, plus the camera-path benchmarks. Those run in CI, and the benchmarks gate each phase.
